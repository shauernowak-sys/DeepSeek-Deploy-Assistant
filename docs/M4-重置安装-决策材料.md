## 0. 先纠正一条上游口径（本轮核实）

上一轮草案与回滚弹窗曾写"回滚后可重新部署，缓存会保留"，**这句不准确**。核对 `deploy-plan.ts` 的 `ctx.created(...)`：

| 路径 | 回滚时 | 依据 |
|---|---|---|
| `runtimes/node/<ver>`、`runtimes/pnpm`、`bin/`（pnpm shim）、`harness/<ver>` | **删除** | `deploy-plan.ts:136/293/309/194` |
| `cache/downloads`（Node 压缩包） | **删除** | `deploy-plan.ts:112`（`ctx.created(paths.downloads)`） |
| `cache/pnpm-store`（pnpm 包存储）、`dsh-home`（profile、QQ 配置）、`state/`（任务与备份）、API 密钥 | **保留** | 未出现在 `created[]` |

**已修正 UI 文案**：回滚弹窗现在写"本次下载的 Node 压缩包会随回滚一起删除，但 pnpm 的包存储不受影响，多数依赖无需重新下载"。

> 这条事实对 Q4 至关重要：**"保留缓存"不是可以勾选的选项，而是现状——`cache/downloads` 已被算作本次产物。**

## 1. 决策门禁带来的硬约束（决定 B 能不能"一键"）

`EnvService.authorize(planId, confirmed)` 的三道校验（`env-service.ts:96-131`）：

1. `confirmed` 必须为 true；
2. `planId` 必须存在（否则 `E_DECISION_REQUIRED`）；
3. `planId` 必须**未过期**（`planTtlMs`）且**未被更新的检测结果取代**（`artifact.seq < latestSeq` → `E_DECISION_STALE`）。

关键点：**校验的是"计划的新鲜度"，不是"磁盘现状"。** 于是方案 B（回滚 + 立即重装）技术上可以复用同一个已确认的 `planId` 重跑计划（步骤里的 `precondition` 会把"已安装"判为需要重装）。

**但这会带来一个产品判断题**：用户在"重置"确认框里点了一次"确认"，是否等于授权了"删除 + 重新安装一个约 150–350 MB 的东西"？PRD §5.2 R1 要求"任何安装/写入前必须用户确认并说明细节"。两种合规路径：

- **B1（保守）**：删除后**重新检测 → 重新出方案 → 用户再确认一次**。合规性最好，但"一键"名不副实（实际是两步）。
- **B2（激进）**：复用同一 `planId`，在确认页里**同时列出"将删除/将重新安装/预计下载与耗时"**，一次确认完成两步。需要产品书面确认"一次确认覆盖删+装"。

## 2. Q1–Q5 逐条决策材料

### Q1：「重置安装」是否等于"回滚 + 重装"？

| 选项 | 含义 | 影响 | 建议 |
|---|---|---|---|
| A | 不提供该入口 | 用"回滚本次创建… → 开始部署"两步替代；成本 0.5 人日（仅文案，**已做**） | ✅ **推荐** |
| B1 | 删 → 重新检测 → 再确认 → 装 | 合规、可解释；两次确认；成本 3–4 人日 | 备选 |
| B2 | 删除 + 复用 planId 直接装 | 一次确认；需产品书面接受"一次确认覆盖删+装"；失败面最大；成本 4–6 人日 | 不推荐 |
| C | 只重置 profile/插件配置 | 会删 QQ 配置（`cordis.patch.yml`）→ 与 G-A2 冲突 | 不推荐 |

**推荐：A。** 理由：现有三步（回滚 / 重试这一步 / 回到上一可用）已覆盖绝大多数"坏了"的场景，而"重置"的增量价值只有"少点一次按钮"。

### Q2：是否允许"重置"清空 profile（含 QQ 与插件配置）？

| 选项 | 后果 | 建议 |
|---|---|---|
| 不允许 | profile 只能通过"回到上一可用"整体回退到某个备份 | ✅ **推荐** |
| 允许 | 等于删用户数据，需 G-A2 书面豁免 + 强制先备份 + UI 明示"会删掉 QQ 登录配置" | 不建议 |

> 事实依据：QQ 配置写在 profile 的 `cordis.patch.yml`；API 密钥在 DPAPI（不在 profile），所以"重置 profile"会丢 QQ 配置但不丢 API Key —— 这种半丢状态最难向用户解释。

### Q3：重装失败时期望什么状态？

| 选项 | 建议 |
|---|---|
| 保持"已回滚 + 失败任务可重试"，不做自动重试 | ✅ **推荐**（与现有 `failed` 语义一致，用户可点「重试失败步骤」或「重试这一步」） |
| 自动重试 1 次 | 不建议：弱网下两次都失败会让用户等更久，且掩盖真实原因 |

### Q4：下载缓存默认保留还是清空？

**现状已定**：`cache/downloads` 属于本次创建产物 → 回滚即删除；`cache/pnpm-store` 保留。

| 选项 | 建议 |
|---|---|
| 保持现状（下载包删、包存储留） | ✅ **推荐**（无需新代码，语义已在弹窗写明） |
| 提供"同时清空 pnpm store"复选项 | 不建议进 V0.1：pnpm store 是跨项目共享缓存，清它影响其它项目 |

### Q5：入口放哪个页面？

| 选项 | 建议 |
|---|---|
| 故障诊断页（修复动作归类） | ✅ **推荐**：部署页已有 5 个动作按钮，再堆会挤压主流程 |
| 部署页与"回滚本次创建…"并列 | 不推荐（正是当前拥挤的原因） |

## 3. 方案 B 的失败路径设计（若产品选 B1）

### 3.1 时序

```
[确认①：将删除 N 个路径 + 将重新安装，列出体积/耗时]
        ↓
rollback(confirmed)            ← 既有能力，只删 created[]，逐路径校验在管理根内
        ↓
re-inspect（EnvService.scan）  ← 必须重新检测：Node/pnpm/Harness 已不存在
        ↓
[确认②：新方案 planId + confirmed]
        ↓
start(planId, confirmed, fresh:true)
```

### 3.2 失败矩阵

| 阶段 | 失败表现 | 期望行为 | 用户可见 |
|---|---|---|---|
| rollback | 文件被占用（Harness 仍在跑） | 中止，**什么都不删**？→ 实际是"删到一半"。因此**前置检查必须是"Harness 已停止"**，未停止则直接拒绝 | "请先停止 Harness 再重置" |
| rollback | 部分路径无法确认归属 | 保留该路径，其余照删，如实报告（既有 `refused` 语义） | 列出保留路径与原因 |
| re-inspect | 检测失败/网络异常 | 停在"已回滚"状态，不自动重装 | "已清理完成，但环境检测失败，可稍后点『开始部署』" |
| 确认② | 用户取消 | 停在"已回滚"，不执行 | 明确"已清理，未安装任何东西" |
| start | 中途失败（下载/解压/安装） | 保留 `failed` 任务与已完成步骤，可「重试这一步」 | 既有失败横幅 + 重试入口 |
| 任意 | 应用崩溃 | journal 已有 `running` 对账逻辑（`reconcileInterrupted`） | 重启后提示"上次中断，可重试" |

### 3.3 必须遵守的 4 条硬规则

1. **不得绕过决策门禁**：重置不能成为第二个执行入口（`task:start` 仍是唯一执行入口）；
2. **删除前必须二次确认**，且确认页列出将删除的路径（复用 `rollbackPreview`）；
3. **必须显式要求 Harness 已停止**（回滚删除运行时目录，被占用会留下半成品）；
4. **不得触碰** profile、`dsh-home`、`state/backups`、API 密钥。

### 3.4 验收标准（可测）

1. 重置后 `listPlugins`/profile 与重置前**一致**（证明没删用户数据）；
2. 重置 → 重装失败 → 任务为 `failed`，可「重试这一步」；
3. 重置全流程中 `task:start` 只被调用一次（证明没有绕过门禁）；
4. `state/backups` 下备份数量不减（证明备份未被清）。

**工作量：B1 ≈ 3–4 人日（含真实链路验证）；B2 ≈ 4–6 人日 + 一次书面确认。**
