## 4. 授权方式（两种，必须分别验收 —— 对应 PRD §8.4）

插件入口 `lib/index.js` 的 `apply()` 逻辑（原文要点）：

```js
let appId = resolveEnv(config.appId, 'QQBOT_APPID');
let appSecret = resolveEnv(config.appSecret, 'QQBOT_SECRET');
if (!appId || !appSecret) { /* 走扫码绑定 ensureCredentials(...) */ return; }
registerBoundCredentialRoutes(...); await bootstrapGateway(...);
```

### 4.1 方式 A：AppID + AppSecret（环境变量注入）

- `resolveEnv(value, key)`：`value` 是字面量则直接用；是 `__FROM_ENV__`（或 `process.env.*` 表达式）则读 `process.env[key]`。
- bundle patch（插件自带 `cordis.patch.yml`）里就是 `appId: __FROM_ENV__` / `appSecret: __FROM_ENV__`，并在注释里声明 `QQBOT_APPID` / `QQBOT_SECRET`。
- **实测**：设置 `QQBOT_APPID=100000000 QQBOT_SECRET=<dummy>` 启动后，**不再打印二维码**（走了"已绑定"分支）→ 证明环境变量确实被插件采纳。
- ⇒ 与 M3.1 的 `apiKeyEnv` 注入方式同构：**DPAPI 存密文 + 启动时注入环境变量，配置文件里不出现明文**。

### 4.2 方式 B：官方扫码绑定

- 无凭据启动时插件打印 ASCII 二维码 + **官方链接**（实测原文）：

```
请使用手机 QQ 扫描上方二维码，完成机器人绑定。
二维码显示异常？点击下方链接，用浏览器打开即可完成扫码:
  https://q.qq.com/qqbot/openclaw/connect.html?task_id=<uuid>&source=dsh-qqbot&_wv=2
```

- 该流程走 `@tencent-connect/qqbot-connector` 的 `connect()`（官方 q.qq.com 授权页），**我们不实现任何扫码协议、不代替用户登录**。
- 宿主形态判定 `isDesktopHost()` = `ELECTRON_RUN_AS_NODE=1 && process.versions.electron`。本产品用 `node.exe` 启动 `dsh`，因此插件认为是**终端宿主**，会使用终端呈现器（打印二维码与链接）→ **我们可以直接捕获这两行来在 UI 里展示**。
- 另有官方降级通道：`QQBOT_BIND_OPEN_BROWSER=1` 时插件自己用系统浏览器打开该链接（`createBrowserPresenter`），适合非技术用户。
- **凭据落盘事实（关键）**：扫码成功 → `persistCredentialsToProfile()` **把 `appId`/`appSecret` 写进 profile 的 `cordis.patch.yml`（明文）**，然后触发 HMR 重载。`BIND_UNBIND`/解绑会从该文件移除。
  - 这与「AppSecret 不写普通配置文件」的硬要求直接冲突（属**插件自身设计**，不是我们的实现选择）→ 见风险 R1 与决策 D1/D2。

## 5. 状态可观测性（M3.2-03 的可行性边界）

| 想知道的 | 可得信号 | 结论 |
|---|---|---|
| 插件是否安装 | `profiles/web/package.json` 依赖 + `dsh plugin --profile web list` 输出 | **可靠**（M1 已实现并测过） |
| 插件是否加载 | `--dump-config` 含 `im-qqbot`（组合层）；启动后 stdout 出现插件自有输出（如扫码提示 / `Bot ready`） | **可靠**（组合层）+ **运行时证据**（stdout） |
| 是否已授权 | 我们自己的 DPAPI 是否有凭据（方式 A）／profile patch 是否有 appId/appSecret（方式 B） | **可靠**（但要区分两种方式，不能只看文件存在就宣称"已连接"） |
| 是否已连接 | stdout 的 `[im-qqbot] Bot ready! appId=...`（插件用 `console.log`，**一定进 stdout**） | **可靠**（成功信号明确） |
| 正在连接 / 失败 / 重连 | 插件用 `logger.info/warn/error` 输出（`Bot disconnected ... reconnecting...` / `permanently ... giving up`）**实测未出现在 stdout** | **不完整**：只能按"有凭据但 N 秒内未 ready ⇒ 连接中/未就绪"，并展示原始输出尾部 |
| 插件自带的 HTTP 状态/配置路由 | `lib/shared/bind-protocol.js` 定义 `/qqbot/im-qqbot/{bind,bind/refresh,bind/manual,bind/unbind,config}`，需 `ctx.inject(['webServer'])` | **在本产品宿主下实测 404**（两次：未绑定、伪造凭据已绑定），即便 `webserver`/`web-runtime` 在组合树里都是启用状态 → **不可依赖**（见 R2） |

`qqbot-nodejs@1.0.5` 的连接机制（读 SDK 源码）：WebSocket 网关 + heartbeat + `RESUME`，`disconnected` 事件带 `willReconnect`，失败走指数退避重试（`retry.js`）。即**断网重连由 SDK 负责**，我们只需观测与提示。

## 6. 配置写入机制（重大发现）

在 `%TEMP%\m32-dshhome`（副本，未动用户数据）里给 profile 层追加：

```yaml
- id: im-qqbot
  config:
    requireMention: false
    groupPrompt: 'LAB-GROUP-PROMPT'
    access:
      groupMode: allowlist
      groupAllow: ['LAB-GROUP-OPENID']
```

`--dump-config` 组合结果：

```yaml
- id: im-qqbot
  name: '@tencent-connect/dsh-qqbot'
  config:
    requireMention: false
    groupPrompt: LAB-GROUP-PROMPT
    access:
      groupMode: allowlist
      groupAllow: [LAB-GROUP-OPENID]
```

**两条结论**：

1. ✅ 我们能用自己的受管块覆盖 bundle `insert` 进来的 `im-qqbot` 条目（与 M3.1 覆盖 `llm-deepseek` 同一机制）。
2. ⚠️ 覆盖是**替换 `config` 整体**，不是深合并 —— 覆盖后 `appSecret`、`textChunkLimit`、`sessionIdleTimeout`、`maxQueue`、`processingTimeoutMs`、`historyLimit`、`debug` 都从组合树里消失了。
   ⇒ 我们写块时必须**写全** `appId/appSecret: __FROM_ENV__` 以及所有我们要固定下来的字段，否则行为会退回 schema 默认值（例如 `streaming` 默认 true、`media` 默认开）。

## 8. M3.2 实施计划（分阶段，逐阶段汇报）

### 第二阶段：插件管理与授权配置（M3.2-01 / M3.2-02）

1. `packages/core/src/qq/`（新）：`version.ts`（版本比较 + 兼容矩阵判定）、`patch.ts`（`im-qqbot` 受管块渲染，**写全字段**）、`state.ts`（状态机）、`messages.ts`（输出行解析：扫码链接、`Bot ready`、重连/失败）。
2. `packages/spec`：新增 `QqStatusSchema` / `QqCredentialsSchema` / `QqConfigSchema` / `QqEmptySchema`；新增错误码 `E_QQBOT_NOT_INSTALLED`、`E_QQBOT_VERSION_MISMATCH`、`E_QQBOT_CREDENTIAL_*`。
3. `apps/desktop/src/main/services/qq-service.ts`（新）：`status()`、`saveCredentials()`、`deleteCredentials()`、`saveConfig()`、`bindLink()`、`relaunchForBinding()`；复用 `Secrets`，键 `QQBOT_APPID` / `QQBOT_SECRET`。
4. `HarnessService`：把 `apiEnv()` 泛化为 `runtimeEnv()`（API Key + QQ 凭据合并），并新增 **stdout 环形缓冲 + 事件**（用于状态与证据展示）。
5. UI 第 5 节改造为「QQ 机器人」：插件状态、版本、凭据表单（掩码）、官方扫码入口（显示官方链接 + "用浏览器打开"）、解绑。

### 第三阶段：连接检测与消息配置（M3.2-03 / M3.2-04）

6. 状态机按 §5 的证据分级；每级都显示**依据**（组合配置命中 / stdout 行 / 进程状态 / 计时），不因配置文件存在就宣称已连接。
7. 消息配置表单：`requireMention`、`groupPrompt`、`directPrompt`、`streaming`、`textChunkLimit`、`historyLimit`、`access.{c2cMode,groupMode,c2cAllow,groupAllow}`、`media.enabled`、`sendFile.restrictPaths`（视觉默认关，需显式开启并填 provider/model）。
8. 写入受管块 + `--dump-config` 回读校验（复用 M3.1 的 `verify.ts` 思路，扩展到 `im-qqbot`）+ 失败回滚。

### 第四阶段：异常恢复（M3.2-05）

9. 失败分类：Harness 未运行 / 插件未加载 / 无凭据 / 有凭据但未 ready（超时）/ 端口不可达。
10. 恢复策略：桌面助手重启 → 从 DPAPI 重新注入（方式 A 免扫码；方式 B 依赖插件已写入的凭据）；Harness 崩溃 → **待决策 D4**（默认：只提示 + 一键重启，不静默自动重启，避免重复建连触发风控）。

### 第五阶段：自动化测试与 M3.1 回归

11. 单测：版本判定、patch 生成（含"必须写全字段"断言）、状态机转换、输出行解析、密钥加密/删除/掩码、日志脱敏、IPC schema 校验、重启恢复逻辑。
12. **M3.1 回归**：现有 132 项必须全绿；额外断言"QQ 配置存在时 API 配置与注入不受影响"（同一 `runtimeEnv` 合并逻辑）。

### 第六阶段：打包与真实 QQ 测试（QQ-GATE-01）

13. 重建安装包 + SHA-256；逐项做 §9 的 6 项真实测试并留存脱敏证据；未做的项保持"未通过"。

## 12. 结论

- M3.2 的技术路径**已可确定**：插件配置写入（受管块，写全字段）+ 凭据 DPAPI + 启动环境注入（`QQBOT_APPID`/`QQBOT_SECRET`）+ 官方扫码链接呈现 + stdout 运行时证据。
- 三个不可控事实必须在产品上显式承认：**扫码会把明文写进插件自己的配置文件**、**插件 HTTP 路由在本宿主不可用**、**重连/失败日志不可观测**。
- 真实 QQ 收发（QQ-GATE-01 的 6 项）目前**全部未验证**，需要真实凭据与人工操作。
