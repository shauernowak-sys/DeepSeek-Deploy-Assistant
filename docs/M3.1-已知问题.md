### K-M3-11 推理模型只返回 `thinking` 块被误判为"响应格式异常"（P1，已修复）

- **现象**（真实 Key 实测发现）：`deepseek-flash` 在 `max_tokens=16` 时把预算全用在 `thinking` 块上，**不返回 `text` 块**；旧解析要求必须有 `text`，于是把一次正常的 200 调用判成 `bad-response`（"接口返回了 JSON，但没有模型回复内容"）。有效 Key 的用户会被误导成"配置写错了"。
- **修复**：`checkReply()` 改为结构判定 —— Anthropic：`type=message` 且 `content` 为非空数组即有效（无文本时说明"返回 N 个内容块（无文本，推理模型只给思考块时属正常）"）；OpenAI 兼容：`choices[0].message` 存在，且 `content` / `reasoning_content` / `tool_calls` 任一有内容即有效。`max_tokens` 16 → 64。
- **回归测试**：`tests/core/api-connection-test.test.ts` 新增 3 例（只有 thinking 块 → ok；`content: []` → 仍 bad-response；只有 `reasoning_content` → ok）。
- 证据同上。

### K-M3-02 密钥只对"由本软件启动的 Harness"生效（P1）

- **原因**：为满足 PRD「明文不落盘」，密钥只以 DPAPI 密文存在，启动 `dsh web` 时通过环境变量注入。
- **后果**：用户若自己在终端运行 `dsh`，该进程拿不到密钥，模型调用会报 `MISSING_CREDENTIAL`。
- **当前对策**：产品定位是"用户只通过本软件使用 Harness"；诊断与提示中未要求用户开终端。
- **可选改进（需产品决策）**：提供"同时写入 Harness 凭据存储（明文 YAML）"的显式开关（默认关闭），并明确告知风险。

## 1b. 验收期发现的缺陷（已修复）

### K-M3-10 未部署就点"启动 Harness"会弹出英文 JS 错误（P1，已修复）

- **表现**（用户实机反馈）：在只装了官方 Harness 桌面端、本产品尚未执行"一键部署"的机器上，点第 2 节"启动 Harness"，弹出 `A JavaScript error occurred in the main process`，内容为 `spawn C:\Users\<user>\AppData\Local\DeepSeekDeployAssistant\runtimes\node\22.23.4\node.exe ENOENT`。
- **根因**（两处叠加）：
  1. `spawnCommand()` 只挂了 `stdout`/`stderr`/`close`，**没有 `error` 监听**。`spawn` 失败时 Node 把 `'error'` 当作未捕获异常抛出，Electron 主进程弹出原始 JS 错误对话框。实测事件序列：`error @2ms ENOENT` → `close @3ms code=-4058`。
  2. 即使不崩，`ready` 的拒绝文案是 `dsh web 提前退出（code=-4058）：`（输出为空），普通用户无法理解，也不提"还没部署"。
- **修复**：
  - `spawnCommand()` 返回 `spawned: Promise<void>`（`'spawn'` 兑现 / `'error'` 拒绝），并在内部吞掉拒绝，主进程不再因 spawn 失败崩溃。
  - `launchWeb()` 监听 `'error'`：`ENOENT` → `找不到 Harness 运行时：<node.exe 路径>。请先完成"一键部署"，再启动 Harness。`；其它错误码同样带码与路径；`ready` 增加 settle 守卫，避免 `error`/`close` 重复结算。
  - `HarnessService.launch()` 新增前置检查：缺 `node.exe` 或 `dsh/lib/bin.js` 时抛 `E_HARNESS_NOT_DEPLOYED`（中文原因 + "先部署"动作，新增错误码与 `DIAGNOSTICS` 条目），不再走到 spawn。
  - 渲染层：未安装时"启动 Harness"按钮禁用并显示"请先完成第 3 节一键部署"；错误面板统一剥离 Electron 的 `Error invoking remote method '…'` 前缀。
- **回归测试**：`tests/adapters/harness-launch-failure.test.ts`（2 例，含"不产生 uncaughtException"断言）、`tests/desktop/harness-service-preflight.test.ts`（2 例，含"只缺 Harness 本体"的分支）。
- **说明**：用户手动安装的官方 Harness（`%USERPROFILE%\.dsh`）**不会被本产品复用**——产品按 PRD 在自己的数据目录部署隔离副本（`%LOCALAPPDATA%\DeepSeekDeployAssistant\runtimes|harness|dsh-home`），两者互不干扰。

## 2. 重要项（P1）

### K-M3-03 模型"是否存在"只能由请求失败推断

- Harness 自述：模型目录是配置元数据，不探测远端。我们的连接测试也没有调用 `/models` 端点（不同网关支持程度不一致），而是用一次最小对话请求的 404/400+model 关键词判断。
- 影响：个别网关对"未知模型"返回 400 且不提 model 字样时，会被归到 `bad-response` 而不是 `model-not-found`。提示仍可行动（"确认接口地址与协议"）。

### K-M3-04 自定义服务仅支持 OpenAI 兼容协议

- `dsh-llm-pi-ai` 实际支持 `openai-completions` / `openai-responses` / `anthropic-messages` 三种 `api`；M3.1 仅开放 `openai-completions`。
- 影响：Anthropic 原生协议的自定义网关暂不能在 UI 中选择（DeepSeek 官方已走 Messages 协议，不受影响）。
- 计划：M3.2/M3.x 增加协议选择（后端已能表达，只需放开 UI 与校验）。

### K-M3-05 只能配置一套"当前生效"的模型

- 现状：单个受管块 + 单个 `agent-default-model`。切换服务即覆盖，不支持多套并存/快速切换。
- 影响：需要多模型的用户要重复填写；不影响正确性。

### K-M3-06 上下文窗口需要用户自己判断（自定义服务）

- 自定义服务默认写 131072，用户可改；写错会导致 Harness 的上下文预算判断偏差（不会崩溃）。
- DeepSeek 官方模板使用 schema 里的 1,000,000，无需用户填写。

## 3. 打磨项（P2）

### K-M3-07 保存后需重启 Harness 才保证生效

- patch 写入后 `--dump-config` 立即反映；运行中的 Harness 依赖 HMR 热重载（默认 bundle 已启用 `dsh-hmr`），但本产品未强制重启以规避"用户正在对话"的中断。
- 建议：M3.2 在保存后提示"若 Harness 正在运行，建议停止后重新启动"（当前文案已提到配置会在部署后生效，未覆盖"运行中"场景）。

### K-M3-08 备份文件不自动清理

- 每次保存会留一个 `cordis.patch.yml.dda-backup-<时间戳>`。体积很小，但长期使用会累积。
- 建议：M3.2 增加"清理旧备份"或保留最近 N 份。

### K-M3-09 Publisher / InstallLocation 仍为空（自 M2.1 延续）

- 与 M3.1 无关；需产品方确认 `author` 主体后再补。
