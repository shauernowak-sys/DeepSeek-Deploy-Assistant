## 3. TASK-01：IPC 接口一致性与无效接口清理

**修改前的问题**

- `preload` 暴露 `apiStoredRefs()` → `api:refs`，主进程**无对应 handler**，一旦调用立即抛 `No handler registered`。
- `plugin:list`、`plugin:install-qq`、`api:status`、`log:export` 四个通道在渲染层**零调用**；其中 `log:export` 还返回过时文案"诊断包打包在 M5 实现"（早已实现）。
- 通道契约没有任何自动化守护，主进程/preload/渲染层可以各自漂移。

**修改后的行为**

- 通道集合三方完全一致：主进程 57 个 handler，preload 57 个 invoke 通道，全部有调用方或事件订阅。
- `task:rollback` 由 `TaskIdSchema` 升级为 `TaskRollbackSchema`（必须 `confirmed: boolean`），并新增只读的 `task:rollback-preview`。
- 新增 `tests/desktop/ipc-contract.test.ts`：直接解析 `register.ts` / `preload/index.ts` / 渲染层源码，断言
  ①每个 preload 通道都有 handler；②不存在无人能调用的死通道；③无重复注册；④事件通道都有主进程发送方；
  ⑤渲染层只调用真实存在的方法；⑥preload 不暴露零调用方法；⑦危险通道必须带确认参数。
- 参数校验用例覆盖 `task:start` / `taskId` / `task:cancel` / `task:rollback` / `diag:export` / `api:save`，包含"拒绝多余字段"。

**保留未删的接口及理由**

- `harness:info`（内部复用 `listPlugins`）、`log:open`：仍被 UI 使用。
- `deploy-plan` / `SnowLuma` 相关通道：M3.3 已验收功能，本轮不动。

## 4. TASK-02：部署任务状态语义修复

**修改前的问题**

`packages/core/src/engine/executor.ts` 在步骤抛错时执行 `finish('paused', { error, pausedByUser: false })`。结果是：任务其实已经失败，UI 却显示"已暂停（可继续）"，用户无法判断是"我暂停的"还是"坏了"，也无法判断该重试还是该回滚。

**修改后的行为**

状态机保持既有词汇（最小改动，不推翻架构），语义收紧为：

| 状态 | 触发条件 | UI 表现 |
|---|---|---|
| `pending` | 尚未开始 | 待开始 |
| `running` | 正在执行 | 进行中 + 当前阶段 |
| `paused` | **仅**用户主动暂停（`pausedByUser=true`） | 黄色横幅"已暂停（你主动暂停）…点继续从下一步开始"，按钮"继续" |
| `failed` | 任一步骤抛错（保留 `error` 原文与失败步骤） | 红色横幅"部署失败：<原因>…失败不等于暂停"，按钮"重试失败步骤" |
| `cancelled` | 用户取消 | 已取消 |
| `rolled-back` | 回滚完成 | 已回滚，与失败明确区分 |
| `succeeded` | 全部步骤完成 | 已完成 |

配套：

1. 失败后**不**再显示为"可直接继续"：主按钮文案变为"重试失败步骤"，并同时提供"回滚本次创建…"。
2. 失败步骤在 journal 中为 `failed` 且带 `message`，恢复时只重跑 `failed` 及其后的步骤（已完成步骤记 `succeeded/skipped` 不重跑）。
3. 失败任务也允许"取消…"（进入已有的取消确认弹窗）。

**测试（`tests/core/task-state-machine.test.ts`，8 项）**：正常部署、主动暂停、步骤失败、失败后恢复、取消、回滚、重复操作（无待执行步骤时 resume 不重跑）、异常退出（journal 停在 running 的步骤被重跑并收敛）。

## 5. TASK-03：危险回滚操作增加二次确认

**修改前的问题**

"回滚本次创建"按钮点击即执行递归删除（Node 运行时、pnpm、Harness 安装目录、下载缓存），无确认、无预览，也不校验 journal 里记录的路径是否真的属于本软件。

**修改后的行为**

1. 点击只调用 `task:rollback-preview`（只读），弹出与"取消部署"同风格的确认窗口。
2. 弹窗明确列出：将删除的路径（`×`）、被保留的路径（`·` 且给出原因）、受管根目录、"你自己的 Harness profile / API 配置 / QQ 凭据与其他数据不在删除范围内"。
3. 只有再次点击"确认回滚并删除"，并且 `confirmed=true` 才会执行；无记录/运行中一律拒绝。
4. 执行后：删除实际发生的路径清单写入日志，任务置为 `rolled-back`，UI **重新读取真实环境**（`env:scan` + `harness:info`），不是只改文案。
5. 失败或被拒绝的路径通过 `refused[]` 返回并在界面列出原因。

**安全校验（`packages/core/src/engine/safety.ts`）**

删除任何一个 journal 路径前都必须同时满足：

1. 是绝对路径，且（分隔符感知地）位于受管根目录 `%LOCALAPPDATA%\DeepSeekDeployAssistant` 内——`...\DeepSeekDeployAssistant-evil` 这类前缀相似目录**不算**内部；
2. 不能是受管根目录本身；
3. 不能是软链接/联接点；
4. 解析真实路径（含"最近存在的父目录"）后仍位于受管根目录的真实路径内——阻断"父目录是联接点"的路径穿越。

不满足任一条 → 拒绝删除并记录原因。**无法确认归属时一律不删。**

**测试（15 项）**：`tests/core/rollback-safety.test.ts`（10 项：分隔符感知、目录内删除、目录外拒绝、前缀相似兄弟目录、根目录本身、相对路径与 `..`、软链接、联接点父目录穿越、已不存在路径、未配置时的兼容行为）+ `tests/desktop/deploy-service-rollback.test.ts`（5 项：未确认不删、确认后只删本次产物且保留用户 profile、预览区分可删/拒绝、混入外部路径时如实报告、无记录时明确拒绝）。

## 6. TASK-04：部署失败与启动异常处理

**修改前的问题**

- `app.whenReady().then(async () => { await createContainer(); ... })` **没有 catch**：容器/清单初始化失败时应用直接退出，用户看到的是"什么都没有"。
- 渲染层没有 ErrorBoundary，任何渲染期异常都会白屏。
- 未处理的 Promise rejection 没有统一出口。

**修改后的行为**

1. 初始化链改为 `app.whenReady().then(bootstrap).catch(reportFatal)`；`reportFatal` 先写脱敏日志（`<userData>/startup-error.log`，`redact()` 处理 `apiKey=`、`sk-…`、`Bearer …` 等），再弹出可读的错误对话框，最后退出——**不再无窗口静默失败**。
2. `unhandledRejection` / `uncaughtException`：有日志时写日志；窗口不存在时升级为致命错误流程。
3. renderer 加载失败（`did-fail-load`）与 renderer 进程退出（`render-process-gone`）都会记录日志并在必要时提示用户。
4. 渲染层新增 `ErrorBoundary`：显示错误摘要 + "重新加载界面" + "打开日志目录" + 可展开技术细节；`main.tsx` 额外兜底记录未捕获错误与未处理 rejection。
5. 所有日志与对话框内容都经过脱敏，**不包含 API Key / Token / 口令**。

**测试（`tests/desktop/startup-guard.test.ts`，5 项）**：脱敏、单行压缩与截断、非 Error 值摘要、日志文件写入（含堆栈、不含密钥）、日志目录不可写时不抛二次异常。

> 边界说明：ErrorBoundary 本身需要 DOM 环境，仓库未引入 jsdom（不为此新增依赖），因此其正确性由类型检查 + 构建 + 实机启动验证覆盖，未新增 DOM 单测。

## 7. TASK-05：配置与敏感数据可靠性

**修改前的问题**

- `secrets.bin` 直接 `writeFile` 全量覆盖：写入过程中崩溃/断点会**截断已保存的凭证**。
- `api-config.json` 同样非原子写入。
- `.dda-backup-*` 备份无限累积。

**修改后的行为**

1. `writeFileAtomic`（`packages/core/src/transfer/fs-utils.ts`）：同目录临时文件 → `fsync` → `rename` 覆盖；Windows 下 `EPERM/EACCES/EBUSY/EEXIST` 重试 6 次；最终失败时删除临时文件并**保持原文件不变**。
2. `secrets.ts` 与 `api-config.json` 均改用原子写；`secrets.bin` 原文件无法解析时，下一次写入前先保留 `<file>.corrupt-<时间戳>` 副本，不静默丢弃未知凭证。
3. 备份保留策略：每次备份完成后只保留最近 3 份，且**先确认新备份已存在再清理**；清理失败只记警告，不影响保存结果。
4. 保存链保持既有顺序：写入 patch → 写入密钥 → 写入配置 → `--dump-config` 回读校验；任一步失败回滚到备份。DPAPI 保护方式未做任何降级。

**测试（10 项）**：`secrets-atomic.test.ts`（密文落盘、无 `.tmp` 残留、写入失败不破坏原凭证、多密钥互不覆盖、损坏副本保留、损坏后可恢复；`writeFileAtomic` 成功/失败各 1 项）+ `api-service-backup.test.ts`（6 次保存后仅留 3 份且最新可读、无 `.tmp` 残留、默认模板不受影响）。

## 11. 下一轮开发建议

不以"任务完成数"判断下一阶段，而以**风险与阻塞**判断：

1. **优先做"安装决策门禁 + 五态检测"（约 7 人日）**：`ROUTE-MULTIPLE/UNKNOWN` 门禁 + 安装确认页（§21.4）+ 系统 Node 复用/五态（D-1/D-6/ENV-001~003）。理由：当前"已有 Harness 的机器仍可盲目重装"是审计认定的 P1 里唯一会造成**用户环境重复污染**的问题；且它复用本轮已建立的 `isWritableProfile` / `deploy-service` 边界，边际成本最低。
2. **随后做 §21 界面骨架（首页/完成页/向导，约 8 人日）**：不做这一步，A14（零基础用户）无法通过，界面仍是"M2 原型"。
3. **插件资源中心（P0）必须在 M4 正式开发前完成一次"前置验证"**：先落地 `PLG-10.2` 元信息 schema + `PLG-1` 本地索引加载 + 坏索引拒绝（约 2.5 人日），验证"索引可加载/字段完整/坏索引拒绝"后再投入详情页与安装编排。理由：这是 PRD §20.2 的 V0.1 最低实现，且 U5/U14 未决时只能随包内置清单，先证明这条路可行。
4. **与开发并行的交付项**：E2E 门禁（固定 `DDA_E2E_ROOT` + 录制回放）、`THIRD_PARTY_NOTICES.md` 与 `licenses/`、面向用户的手册与排障文档、G-B1..G-B5 书面决策。

**一句话**：本轮把"会误导用户/会删错东西/会静默失败"的坑填平了；下一轮应继续**降低用户误操作风险**，而不是先增加功能数量。
