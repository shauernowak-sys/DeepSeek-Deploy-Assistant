## 1. 阻塞项（P0）

### K-M2-01 QQ-GATE-01 仍未通过

- **状态：** 未通过（自 M1 延续，M2 未改变）
- **已验证：** 插件安装、插件加载、绑定二维码/绑定链接生成
- **未验证：** 真实扫码、真实消息收发、图片消息、断线重连、重启后恢复
- **原因：** 无真实 QQ 凭据；用户明确禁止以 Mock 代替真实核心链路验收
- **影响：** 不得对外宣传"官方 QQ 完整可用"，不得作为已完成功能销售
- **解除条件：** 拿到真实 AppID/AppSecret 与一部可扫码手机，按 PRD §18 门禁逐项实测

### K-M2-02 第二环境（Windows 11 干净机）验证未执行

- **状态：** 未执行
- **原因：** 本机为 Windows 10 19045，无 Win11 环境或虚拟机可用
- **影响：** "Win11 支持"仍为**待验证**结论；不能用开发机缓存结果替代
- **解除条件：** 一台无 Node/pnpm/Harness、非管理员、国内网络的 Win11 机器，按 [M2-测试报告 §4](./M2-测试报告.md) 场景重跑

### K-M2-03 CI 实跑（已解除）

- **状态：** 已解除 —— 2026-11-02 推送仓库后首次实跑暴露 `ERR_PNPM_IGNORED_BUILDS`，修复后 **run #2 全绿**
- **根因：** pnpm 11 已把 workspace 级设置迁到 `pnpm-workspace.yaml`，旧键 `onlyBuiltDependencies` 不再生效，`pnpm install --frozen-lockfile` 在 `CI=true` 下直接失败
- **修复：** 改用 `allowBuilds`（`pnpm approve-builds` 生成的标准形式）；移除 `package.json` 中已不被读取的 `pnpm` 字段
- **证据：** [evidence/m2-ci-run2-quality.log](./evidence/m2-ci-run2-quality.log) —— Quality gate（checkout / pnpm / Node / install / typecheck / 60 单测 / 许可证）+ Build installer 两个 job 全 success，产物 `deepseek-deploy-assistant-nsis`（78.3 MB）可下载
- **遗留：** 后续新增依赖若含构建脚本，需要把包名加入 `allowBuilds`，否则 CI 会以同样错误失败（属预期保护）

## 2. 重要项（P1）

### K-M2-04 API Key 真实连接测试缺失

- **现状：** 支持本地输入、DPAPI 加密保存、写入 Harness 配置；健康探测仅覆盖本地 `dsh web` 存活/鉴权/可用，**不包含用用户 Key 真实调用一次 DeepSeek API**
- **风险：** 用户 Key 填错时，界面无法在部署阶段给出"鉴权失败"的明确结论（PRD §11 要求）
- **建议：** M3 补 `POST /v1/chat/completions` 最小探针，错误分类为 401/403/429/网络/余额，并把结果写进诊断报告（脱敏）

### K-M2-05 安装包未做代码签名

- **现状：** S0 阶段，`deepseek-deploy-assistant-0.2.0-x64.exe` 未签名（非管理员环境无法解压 winCodeSign 工具链）
- **影响：** SmartScreen 首次运行会出现"未知发布者"提示
- **计划：** 按 PRD §13 的 S0 → S1（OV）→ S2（EV）阶段推进，签名不影响功能

### K-M2-06 安装版 exe 的 `FileVersion` 显示 `33.4.11`

- **原因：** `win.signAndEditExecutable:false` 同时关闭了版本资源写入
- **影响：** 仅"属性 → 详细信息"处显示异常；注册表 `DisplayVersion=0.2.0`、安装器文件名为 0.2.0，功能与升级判断不受影响
- **建议：** 引入签名后再开启 rcedit（需管理员或签名权限）

### K-M2-07 官方 Desktop 四态检测未实机验证

- **现状：** 检测逻辑与"绝不修改 Desktop profile"的约束已实现（CLI 只操作自己的 `dsh-home`），但本机未安装官方 Desktop，四态场景未逐一实测
- **风险：** Desktop 已存在时的冲突提示文案与路由判断未经验证
- **解除条件：** 在装有官方 Desktop 的机器上跑四态矩阵（仅 CLI / 仅 Desktop / 两者 / 均无）

### K-M2-08 插件资源库 / 国内三层下载 / 离线闭包未实现

- **现状：** 当前只安装基线与 QQ 插件，来源为 npm 镜像 + 官方源，SHA-256 校验与断点续传已具备
- **影响：** PRD §10 描述的"我方资源库 + 可信公共镜像 + 官方源"三层优先级与离线包尚未落地
- **计划：** M3 范围，未对外宣称

## 3. 打磨项（P2）

### K-M2-09 取消对正在运行的 pnpm 子进程非强制终止

- **行为：** 取消信号在**步骤边界**生效；pnpm 安装阶段点取消，最多需等待该步骤结束（实测约 65 s）
- **原因：** 强杀 pnpm 会留下半写入 `node_modules`，风险高于等待
- **缓解：** UI 在取消确认后提示"正在结束当前步骤"，日志记录 `检测到取消请求：本步骤将在退出后停止`

### K-M2-10 取消后保留 pnpm 缓存（设计选择）

- **现状：** `cache/pnpm-store`、`cache/downloads` 中的下载缓存按设计保留，以便下次安装更快
- **注意：** 这些目录不属于用户数据；如需彻底回收，由用户在"清理缓存"（M3）中处理
- **UI 已明示：** "下载与包缓存会保留，以便下次安装更快"

### K-M2-11 卸载后残留空程序目录

- **现象：** 静默卸载后 `%LOCALAPPDATA%\Programs\DeepSeek Deploy Assistant` 目录仍存在，**内部文件数 0**
- **原因：** NSIS 卸载器运行时所在目录被自身占用
- **影响：** 无功能影响；重装可正常复用该目录
- **处置：** 已记录，未改动打包脚本（改动会牵动卸载稳定性，收益低）

### K-M2-12 失败后无自动重试/自动恢复向导

- **现状：** 失败后提供"继续"（断点续跑）、"重新部署（修复）"、"导出诊断"三个手动入口
- **计划：** 自动重试策略与"一键修复建议"列入 M3 体验优化
