### 1.5 审计发现的架构问题及处理

| 问题 | 风险 | 处理 |
|---|---|---|
| A-1：个人 QQ 服务把"检测 + 插件安装 + 配置写入"塞在一个类里 | 加入安装/启动后会变成不可测的巨类 | 拆成 `snowluma/{release,download,install,config,process,health,deploy,uninstall}`，全部依赖注入 |

| A-5：官方 WebUI 初始口令只在控制台打印一次 | 用户拿不到口令 | 主进程捕获并在内存保留，仅用户点击时展示、不落盘不写日志 |

## 2. 许可与合规闸门（本阶段最关键的产品约束）

### 2.1 条款核实（原文，2026-11-03 从上游仓库直接拉取）

`EULA.md` §5.4（中文）：

> 除事先取得著作权人的书面授权外，您仅可为 `LICENSE` 允许的非商业用途，以专有组件随本软件提供的形式运行该组件；不得复制、修改、单独再分发或再许可该组件。**将其并入第三方安装包或 Docker 镜像、通过自动化脚本部署**，或者将其用于任何商业用途，**均须事先取得书面授权**。

英文同条：

> … **Incorporating it into a third-party installer or Docker image, deploying it through an automated script**, or using it for any Commercial Use **requires prior written authorization**.

结论：**"自动下载 + 自动解压安装 + 自动写配置 + 自动启动"整体属于"通过自动化脚本部署"**，未获书面授权时不得实施。这与产品目标（降低普通用户门槛）确实冲突，但不是技术问题，不能用工程手段绕过。

### 2.2 代码里的落点（fail-closed，单一开关）

- 唯一开关是清单的 `authorizationRef`（`SnowLumaManifestSchema` → `decideManifestAutomation`）。
- 未登记时：`SnowLumaDeployRunner` 把 `release/download/install/configure/start` 标记为 `blocked`，附带条款原文与"未登记书面授权"证据；**不产生任何下载/写入/进程**。
- 已登记时：全流程按普通步骤执行（同样的代码路径，单测覆盖到 `done`）。
- 本仓库的清单**保持 `authorizationRef` 为空**：不宣称、不伪造、不留"测试用授权号"。

### 2.3 未授权时仍可完成的部分（已实现）

| 能力 | 是否受限制 | 实现位置 |
|---|---|---|
| 官方入口（Releases / LICENSE / EULA / WebUI） | 不受限 | `personal:open` 白名单 |
| 用户自行安装后的只读检测与结构校验 | 不受限 | `detectSnowLuma` / `inspectExistingInstall` |
| 适配插件 `dsh-qq-link` 安装与端点/令牌写入 | 不受限（操作的是我们自己的 Harness 插件） | `applyBridgeEndpoint` / `link` 步骤 |
| OneBot 真实接口探测（`get_login_info`） | 不受限（只读） | `probeOneBot` / `verify` 步骤 |
| 进程状态、配置现状、配置备份恢复 | 不受限 | `process` / `config` 服务 |
| 卸载（六类数据分离） | 不受限 | `uninstallSnowLuma` |

### 2.4 明确不做

- 不代用户接受 EULA/PRIVACY：启动时主动删除 `SNOWLUMA_ACCEPT_EULA` / `SNOWLUMA_ACCEPT_PRIVACY` 环境变量（`process.ts`），协议由用户本人在 WebUI 勾选。
- 不修改上游可执行文件、不注入、不绕过授权/激活机制。
- 不打包、不镜像、不再分发 SnowLuma 任何字节（安装包只从官方 Releases 运行时下载）。

## 8. 未完成事项与阻塞项

### 阻塞 1：SnowLuma 著作权人书面授权（决定性）

- **具体位置**：`snowluma.json` 的 `authorizationRef`（EULA §5.4）。
- **真实错误信息**：不适用（这是合规闸门，不是程序错误）。
- **已尝试**：核实条款原文（中英）、把自动化隔离为独立模块、fail-closed 开关、UI 明确披露。
- **可行替代**：用户自行从官方 Releases 下载解压 → 「选择 SnowLuma 目录」→ 我们做只读校验 + 适配插件配置 + 真实连通检测（已实现）。
- **对最终体验的影响**：**有**。普通用户仍需自己下载解压一次（约 43 MB），不能"点一下就装好"。

### 阻塞 2：真实 QQ 账号与扫码登录（验收性）

- 需要用户的个人 QQ 账号、手机 QQ 扫码、以及一个"发消息的第二个账号/设备"。
- 本轮已把"人工确认"设计成**不可自动置位**的按钮（`messageVerifiedAt` 只能由用户点击产生）。
- 因此 QQ-GATE-02 的 #2~#11 无法由代码侧代替验证。

### 阻塞 3：真实模型调用

- 依赖阻塞 1/2（消息到不了 Harness）与用户自己的 DeepSeek API Key（M3.1 已支持）。

### 已知限制（非阻塞）

1. 上游未提供签名，只有我们自己计算的 SHA-256 与 GitHub API `digest` 双重比对；无法证明"上游构建机未被攻破"。
2. `link` 步骤在 Harness 未启动时会失败并提示先启动 Harness（而不是假装成功）——这是刻意设计。
3. 真实重装/升级路径（旧版本 → 新版本）只做了同构 fixture 测试，未用两个真实上游版本对跑。
4. UI 冒烟在隔离的 `LOCALAPPDATA`（`D:\tmp-dda-ui`）中进行，不污染用户真实配置。

## 9. 最终回答

> **普通 Windows 用户是否已经可以通过 DeepSeek Deploy Assistant，完成个人 QQ 的自动部署和真实双向消息收发？**

**还没有。**

按真实证据分别回答：

| 问题 | 答案 | 依据 |
|---|---|---|
| 自动部署的**工程能力**是否已具备？ | **是**。版本核对、下载、解压安装、配置、启停、联通、验收的代码全部实现并通过 43 个专项用例（40 核心 + 3 接线）+ 1 个官方真包门控用例 | [m33-real-package.log](./evidence/m33-real-package.log)、[m33-full-tests.log](./evidence/m33-full-tests.log) |
