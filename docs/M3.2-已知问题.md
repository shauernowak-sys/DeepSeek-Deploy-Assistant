## 2. 验收期发现的缺陷

### K-M3.2-13 点"用官方扫码绑定"只有一句提示、没有可见动作（P1，已修复）

- **现象**（用户实机反馈，2026-11-03）：「点这个按钮，软件没有任何反应，提示会有，但是没有动作」。产品日志显示用户共点了 3 次（17:53 / 18:50 / 19:05），每次 Harness 都成功重启，但界面上没有二维码、也没有打开浏览器。
- **根因（三处叠加）**：
  1. 二维码与官方链接只出现在折叠的「插件输出」区，**不在正文可见**；
  2. 「用浏览器打开官方授权页」按钮依赖 `bindUrl`，而界面 4 秒才轮询一次，用户在看到提示的那几秒内按钮还没出现 → 观感就是"没动作"；
  3. 插件自带官方降级通道 `QQBOT_BIND_OPEN_BROWSER=1`（`createBrowserPresenter`）**没有启用**，所以浏览器不会自动打开。
  4. 更糟的是：无论插件有没有真的生成二维码，按钮都返回"已启动官方扫码流程"——**假成功**，把失败伪装成了正常。
- **修复**：
  - 扫码模式改为在子进程环境里**显式置空** `QQBOT_APPID`/`QQBOT_SECRET` 并设置 `QQBOT_BIND_OPEN_BROWSER=1` → 插件走官方扫码分支且**自动打开官方授权页**；
  - 界面新增醒目「官方扫码授权」面板：二维码（`pre.qr` 等宽渲染）+ 官方链接 + 「用浏览器打开官方授权页」/「重新生成二维码」/「取消扫码」+ 尝试次数；
  - 25 秒内没拿到二维码 → 相位变 `failed`，**给出具体原因**（插件无任何绑定输出 / 进了扫码但没生成链接 / 二维码过期未刷新），并提供"重新生成"；
  - **不再删除** DPAPI 里已保存的 AppID/AppSecret（改为环境置空），点「取消扫码」立即回到已验证成功的路径；
  - QQ 运行事件（扫码/就绪/重连/放弃）现在会**脱敏写入产品日志**，便于事后复核（此前只在内存里）。
- **回归测试**：`tests/core/qq-status.test.ts` 新增 7 例（超时/两种失败原因/拿到链接不算失败/二维码下发/二维码抽取×2）；`tests/desktop/qq-service.test.ts` 新增 4 例（不删凭据+取消恢复、重新生成累计次数、扫码模式不误判 connecting、保存凭据退出扫码模式）。
- **修复后实跑验证**（新构建，点击界面真实按钮）：二维码 22 行渲染在正文 `pre.qr`（不在折叠区）、面板含「用浏览器打开官方授权页 / 重新生成二维码 / 取消扫码」、重新生成后尝试计数 2、取消后凭据来源回到 `dpapi` 且 Harness 按原凭据重启。证据：[m32-qr-fix-verify.log](./evidence/m32-qr-fix-verify.log)。失败分支（25 秒无二维码）由单测覆盖，未做真实等待触发。

## 3. 上游限制（不是我们的实现缺陷，但会限制能力）

### K-M3.2-02 插件自带的 HTTP 状态/配置路由在本产品宿主下不可用（P1）

- 插件源码里有 `/qqbot/im-qqbot/{bind,bind/refresh,bind/manual,bind/unbind,config}`，通过 `ctx.inject(['webServer'])` 注册；在本产品（`dsh web` CLI 宿主）实测 **404**（未绑定、伪造凭据已绑定两种状态都试过），而 `webserver`/`web-runtime` 在组合配置里都是启用状态。
- **影响**：不能用它做状态/配置/解绑，只能改用「受管块写入 + 插件 stdout 证据」。
- **处置**：已按替代方案实现；若上游后续修复，可平滑切换。

### K-M3.2-03 连接过程日志不可观测（P1）

- 插件用 `ctx.logger` 输出 `Bot disconnected … reconnecting` / `permanently … giving up`，实测**不进 stdout**；只有 `console.log('[im-qqbot] Bot ready! appId=…')` 一定可见。
- **影响**：「重连中/失败」只能靠已捕获的 ready 信号 + 就绪超时（90s）推断；失败原因看不到细粒度文本。
- **处置**：UI 同时展示插件输出尾部；不臆造状态说明。

### K-M3.2-04 扫码成功后插件把 AppSecret 明文写入 profile（P1，产品已披露 + 提供迁移）

- `persistCredentialsToProfile()` 会把 `appId/appSecret` 写进 `dsh-home/profiles/web/cordis.patch.yml`（明文）。
- **处置（决策 D1/D2）**：
  - UI 在检测到明文时显示黄条警示，并在文案里说明"这是插件自身行为"；
  - 提供「迁移到加密存储」：读明文 → 写入 DPAPI → 用 `__FROM_ENV__` 覆盖受管块 → 重启 Harness 使环境注入生效；
  - 未迁移前，任何 UI/日志都不回显 AppSecret（只回显掩码）。
- **残留风险**：用户若拒绝迁移，明文仍在磁盘上（属其选择，且是插件行为）。

### K-M3.2-05 `qqbot-connector@1.2.0` 为 UNLICENSED（P0，自 M1 延续）
- 不能打包/镜像该依赖；只能在线安装。UI 与文档已声明。离线安装场景仍阻塞。

## 4. 重要项（P1）

### K-M3.2-06 无开机自启，"Windows 重启后恢复"需用户手动打开助手（P1）

- 决策 D4 选择"不自动重启"，因此也不做开机自启；Windows 重启后需要用户打开助手 → 启动 Harness。
- 恢复本身是自动的（DPAPI 凭据重新注入，方式 A 免扫码），只是"启动"这一步要用户点一下。

### K-M3.2-07 访问控制白名单需要 OpenID，普通用户不易获取（P1）

- 插件要求 `c2cAllow`/`groupAllow` 填 QQ OpenID（不是 QQ 号），产品当前只能让用户手工粘贴。
- **建议**：M3.3 起考虑从插件输出/日志解析出"新会话 openid"并提示加入白名单（需要先验证可行性，不得臆造）。

### K-M3.2-08 视觉理解默认关闭（P1，决策 D5）

- `media.enabled` 负责接收/下载图片；`vision.enabled` 需要另配 provider/model（如 pi-ai + 视觉模型）。本轮只开放"接收"，不承诺"看懂"。
- DeepSeek 官方模型是否支持图片理解未验证，UI 未提供开关（避免给出不可用选项）。

### K-M3.2-09 群聊流式回复始终关闭（P1，插件限制）

- 插件 schema 明确"群聊始终不启用流式"；UI 文案已写清，避免用户误以为设置无效。

## 5. 打磨项（P2）

### K-M3.2-10 插件输出里的二维码为 ASCII 块，界面用 `<pre>` 展示（P2）

- 二维码在窄窗口下可能显示不全；已同时提供 q.qq.com 官方链接与「用浏览器打开官方授权页」按钮作为主路径。

### K-M3.2-11 插件的运行数据在 `~/.dsh-qqbot/`（产品数据目录之外）（P2）

- 包含 `workspace/`（Agent 工作目录）、`media/`（下载的图片文件）、`model-prefs.json`。
- 卸载本产品**不会**删除这些（符合"不删用户数据"原则），但也没有 UI 提供清理入口。

### K-M3.2-12 未做端到端 UI 自动化（P2）

- 目前 UI 验证靠 CDP 驱动 + 手工检查文本；没有引入 Playwright/组件测试框架（避免为本轮引入新工具链）。
