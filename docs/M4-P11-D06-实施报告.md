## 1. P-11 失效代理检测

### 1.1 问题

前置验证 §0.3.1 实测：VPN 客户端关闭后 `HTTP(S)_PROXY` 仍指向死端口时，`npm view` 从 <1 s 退化到 **70.6 s**；而 `dshEnv()` 把 `process.env` 原样传给 dsh 子进程。

### 1.2 实现（[packages/adapters/src/process/proxy.ts](../packages/adapters/src/process/proxy.ts)）

| 函数 | 行为 |
|---|---|
| `parseProxySettings(env)` | 读 `HTTP_PROXY/HTTPS_PROXY/ALL_PROXY` 及小写变体；同名只取一次；非 http(s) 或无法解析的值忽略 |
| `probeProxy(url)` | TCP 连接探测（默认 1.5 s 超时，可注入 `connectImpl`），失败即判不可达 |
| `findDeadProxySettings(env)` | 返回 `{ dead, reachable }` |
| `stripProxyEnv(env, names)` | 返回**副本**并删除指定变量；`NO_PROXY` 原样保留 |
| `describeProxyReport()` | 日志文案（"不可用（仅在本软件子进程中剔除）"） |

接线：

1. **应用启动**（[container.ts](../apps/desktop/src/main/services/container.ts)）：探测一次（1.2 s 超时），结果存 `Container.childEnvExclusions`，并写日志。
2. **dsh 子进程**（[cli.ts](../packages/adapters/src/harness/cli.ts)）：`dshEnv()` 新增 `proxyExclusions`，只在返回的 env 上删除；**不修改** `process.env`。
3. **部署计划**：新增 `check-proxy` 步骤（第一步），日志说明"已从本软件启动的子进程剔除: …（未修改系统设置）"。
4. **Harness 启动/安装**：`HarnessService.getCli()` 同样传入剔除清单。

> 明确不做：不调用 `setx`、不改注册表、不 `unset` 用户环境；用户自己开的代理依旧对其他程序生效。

### 1.3 顺带修正：git spec 的 `&`

`assertArgsSafe()` 之前把 `&` 一律当 shell 元字符拒绝，导致 D03 产出的 `git+https://…&path:/dir` 无法安装。现在：`git+` 开头的 spec 允许 `&`（pnpm 的参数分隔符），其它 shell 元字符仍拒绝；普通参数里的 `&` 仍拒绝。

### 1.4 测试（`tests/adapters/proxy.test.ts`，11 例）

解析/去重、可达性探测、死代理识别、`stripProxyEnv` 不改原对象、`dshEnv` 只改副本、未给清单时行为不变、git spec 的 `&` 放行与其它元字符拦截。

## 2. D06 国内源策略

### 2.1 回退（已在前一批完成，本批补齐可观测性）

`installWithRegistryFallback()` 现在返回：

```ts
{ registry, attempts, history: [{ registry: 'l2-npmmirror', url, ok: false, durationMs, error }, …] }
```

日志每层打印"从<源>安装（1/2）"→ 失败"<源>不可用（N ms），切换到下一层"，成功"已从<源>安装（N ms）"。诊断导出可复用该结构。

### 2.2 tarball 实际 host：能做与不能做

**不能做：** pnpm 11 的 `append-only`/`debug`/`NODE_DEBUG=http` 输出里都**没有** tarball URL（本批实测三种方式），锁文件对默认源也只记 integrity。

**因此采取两件事：**

1. `extractTarballHosts(text)`：只要 CLI 输出了 URL 就统计（按 host 计数），没有就如实输出"未取得 tarball host（pnpm 未输出下载地址）"——**不用 0 假装"全部单源"**。
2. `listMetadataRegistrySources(cacheDir)`：pnpm 把每个源的元数据分别缓存在 `<cache>/<vN>/metadata/<编码后的 registry>`，据此可判定"本次安装实际问了哪些源"。目录名解码按 host 还原（实测 `https%3A+registry.npmjs.org` → `https://registry.npmjs.org`）。

安装结果新增 `tarballHosts`，步骤 5 的明细里直接写出 host 统计。

### 2.3 干净缓存复测（本次实测，2026-11-04）

新增工具 [scripts/registry-probe.ts](../scripts/registry-probe.ts)（`npm run probe:registry`）：每次在临时目录里用**全新 store + 全新 cache** 安装锁定版本，输出耗时与"实际询问的 registry"。

| 源 | 结果 | 耗时 | 实际询问的 registry |
|---|---|---|---|
| `https://registry.npmmirror.com/` | 成功（51 包） | **2.0 s** | 仅 `npmmirror` |
| `https://registry.npmjs.org/` | 成功 | **7.6 s** | 仅 `npmjs` |

**结论：** 隔离缓存后不再出现"配置镜像却从官方源下载"——前置验证 §4.3 的混源现象与 pnpm 跨源元数据缓存复用的假说一致。但这是**解释**，不是**承诺**：旧缓存（`%LOCALAPPDATA%\pnpm-cache`）仍可能造成混源，所以文案继续写"镜像优先、官方兜底"，不写"全部国内下载"。

> 复测命令：`pnpm run probe:registry` / `pnpm run probe:registry -- --source=official`（需网络，不进 CI）。

### 2.4 L1 接口位与计划快照

- `REGISTRY_L1_SLOT = { id: 'l1-managed', blockedBy: 'U5' }`：只表示"这里将来会有一层"，`registryPlan()` 永不返回它；单测对两种偏好顺序都断言了这一点。
- `registryPlan()` 逐字段快照测试（id/url/label/顺序），防上游行为变化导致静默改源。

### 2.5 测试

- `tests/core/registries.test.ts`（9）：计划快照、L1 不出现、尝试历史（源/成败/耗时/错误）、回退与不回退分支。
- `tests/core/source-report.test.ts`（5）：host 统计、空输出文案、单源识别、目录名解码、metadata 源列表。
- `tests/core/install-plan.test.ts`（17）：新增"tarball host 进入步骤明细与 outcome"。
