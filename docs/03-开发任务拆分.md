# 03 开发任务拆分

状态：草案 V0.1 · 计划基线：2026-11-02
依赖文档：[01 项目结构设计](./01-项目结构设计.md) · [02 开源项目复用盘点](./02-开源项目复用盘点.md)

---

## 1. 拆分原则

1. **先验证、后编码。** M0 全部是"能不能做"的验证，任一致命项不通过就调整范围，而不是硬写。
2. **每个阶段有可演示的交付物 + 明确门禁**（Gate），门禁不通过不进入下一阶段。
3. **垂直切片**：M1 就能跑通"下载 → 校验 → 解压 → 验证"的完整链路，而不是先写完所有抽象。
4. **不交付未验证能力**：任何任务未通过其验收标准，状态标记为"未完成"，不允许以"接口已留"计入交付。
5. **估算单位为人日**（1 人日 = 6 小时有效工作），按 1 名 Electron 全栈 + 1 名前端 + 0.5 名测试计。

|---|---|---|---|---|---|

                   └─► M4 ──┴─► M5

若 V11 判定离线不可行 → Gate 4 的"断网安装"验收项降级为"弱网可安装"，并在产品文案中移除"完全离线"表述。

## 9. 关键路径与风险

**关键路径：** V05（国内网络） → A03（下载器） → B01（Node 适配） → C01（Harness CLI） → D03（安装编排） → E01（回归）

| # | 风险 | 概率 | 影响 | 对策 |

| 1 | 国内无法稳定访问 npm / nodejs.org | 高 | 阻断 Gate 4 | M0 必须先测；必要时提前部署国内资源服务器（本项应视为**外部依赖**，不是开发任务） |

## 10. 明确不做（防范围蔓延）

- 不做 Harness 本体、不做 DSH Desktop、不做 Agent 框架、不做模型服务。

- 不做用户账号体系、社区、云端控制。
- 不做自动更新第三方插件（V0.3 再议）。
- 不做系统级（all-users）安装。

## 13. 跨阶段工程策略（本轮新增）

### 13.1 Windows 代码签名：三档策略

| 档位 | 做法 | 成本（量级） | 适用条件 | 后果 |
|---|---|---|---|---|
| **S0 不签名** | 仅出 ZIP 绿色版 + 明确提示 | 0 | 内部验证、3 人外测 | SmartScreen 强拦截；不能作为对外正式发布 |
| **S1 标准 OV 证书** | EV 之外的组织验证证书，用 `signtool` + 时间戳签名 exe/安装器 | 一次性约 ¥2–4k/年 + 每次签名流程工时 | 有公司主体、可提供营业执照 | 需积累下载信誉；首月仍可能被拦，2–4 周后改善（**具体表现需 V02 实测记录**） |
| **S2 EV / 云签名** | EV 证书或云 HSM 签名服务（官方 Desktop 即用"公开证书 + SignTool + 容器 + PIN"模式） | 约 ¥6–12k/年 + 服务费 | 长期正式发行、需要最快建立信誉 | SmartScreen 立即生效，但证书保管要求高、CI 需专用凭据 |

**阶段性落地**：M1–M4 用 S0（只在内测渠道分发，产物名带 `-unsigned`）；M5 前按 E08 决策切 S1 或 S2；
无论选哪档，`electron-builder` 的签名配置与时间戳服务必须在 CI 里预先打通（避免发布日才发现凭据问题）。
（价格仅为量级估算，以询价为准，不作为采购依据。）

### 13.2 国内资源服务器：最低可行方案

| 项 | 最低方案 | 说明 |
|---|---|---|
| 形态 | 单地域对象存储 + CDN（如 COS/OSS + CDN），**只做镜像转发** | 不做二次打包、不改文件内容、不内嵌任何 `UNLICENSED` 依赖 |
| 容量 | 核心基线 &lt; 1 GB（Node zip 36 MB + 插件 tgz 及其允许依赖 + 索引与图标） | 若未来引入更大运行时（Python/FFmpeg）再扩容 |
| 带宽 | 按量计费；V0.1 目标是"够用即可"，不需要预留峰值 | 下载集中在安装时刻，可用 CDN 缓存命中摊平 |
| 成本构成 | 存储（GB·月）+ 下行流量（GB）+ 请求数 + 备案/证书（0，用现有域名） | 以上三项为**唯一**持续成本；不产生服务器运维人力（无计算实例） |
| 运维 | 每日定时同步脚本 + 一致性校验（对每个对象比对上游 sha256） | 由 `scripts/fetch-offline.ts --verify` 完成 |
| 回退 | 主源（官网/registry）→ 国内镜像 → 用户手动选择本地文件 | 镜像故障不影响"能装"，只影响"装得快" |

> 该方案刻意不引入计算资源与代理服务：代理会带来合规与稳定性风险，且违反"优先复用成熟开源项目/官方渠道"的原则。

### 13.3 第三方许可检查机制（工程化，不靠人工记忆）

1. **数据源**：`pnpm list --prod --depth Infinity --json` 得到依赖闭包 → 逐项取 `license` 字段（registry 元数据 + 本地 `LICENSE` 文件双重确认）。
2. **规则**：见 [01 §11.6](./01-项目结构设计.md)（允许清单 / 灰名单 / `UNLICENSED` 直接阻断）。
3. **卡点**：CI（PR 级）+ 打包前（发布级）两次执行 `license-gate`；产物附带 `THIRD_PARTY_NOTICES.md`。
4. **人工复核**：灰名单条目需在 `licenses/allowlist.json` 里带 `reviewer`、`date`、`rationale` 三个字段，缺一即失败。
5. **变更告警**：任一已允许包的 `license` 字段发生变化（上游改许可）时，CI 必须报错并阻断发布。
