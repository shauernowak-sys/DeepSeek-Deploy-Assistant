## 3. 五个决策点的落实情况

| 决策 | 落实情况 |
|---|---|
| D1 两种授权都支持，扫码路径必须显著提示明文风险 | 已实现：黄条警示 + 文案说明"插件自身行为"；文案出现在 `credentialSource=profile` 时 |
| D2 实现「迁移到加密存储」 | 已实现：`qq:migrate` → 读明文 → DPAPI → `__FROM_ENV__` → 重启 Harness → 回读校验，失败回滚 |
| D3 访问控制保持插件默认（open/open/@必需） | 已实现：`DEFAULT_QQ_SETTINGS` 与插件 schema 默认一致，UI 可改 |
| D4 不自动重启，给一键重启 | 已实现：`restart()` 仅在"保存凭据/扫码/切换注入模式"等显式操作时触发；崩溃不自动拉活 |
| D5 只做图片接收与文件回传，视觉默认关 | 已实现：只写 `media.enabled`/`sendFile.restrictPaths`；`vision` 未暴露 |
| 追加要求：扫码不得影响已验证的 AppID/AppSecret 路径 | **已实现并回归覆盖**：扫码只把子进程环境置空（不删 DPAPI），点「取消扫码」立即恢复；4 项测试断言 |

## 4. 结论

**M3.2 的功能实现与工程闭环完成，且已拿到两条真实链路证据**：

- 插件管理、两种官方授权方式、DPAPI 凭据 + 环境注入、10 相位状态机、消息配置写入与回读、异常恢复入口，均已实现；**方式 A（AppID/AppSecret）+ 私聊对话已由用户实机验证通过**。
- 自动化测试 174 项通过（M3.2 新增 42 项），M3.1 的 132 项全绿 → **API 配置与真实调用能力无退化**；两个受管块（`llm-deepseek`/`agent-default-model` 与 `im-qqbot`）在真实 `--dump-config` 中并存且互不覆盖。
- 验收期发现并修复了扫码入口的假成功缺陷（[K-M3.2-13](./M3.2-已知问题.md)），并顺带把 QQ 运行事件落进产品日志，便于事后复核。
