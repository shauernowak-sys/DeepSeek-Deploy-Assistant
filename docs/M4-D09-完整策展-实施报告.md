## 1. 为什么"候选"必须与"可安装"分开

PRD §10.1 冻结「只提供经过验证的核心插件套装，不追求数量」。如果为了显得丰富而把未验证插件塞进 `index.json`，就等于对外宣称"这个组合能装"——这正是 CR-5 与 Gate 4 ⑤ 要禁止的。

因此本轮的分层是：

| 层 | 内容 | 是否进 `index.json` | 能否安装 | 谁消费 |
|---|---|---|---|---|
| `CATALOG.entries` | 验证通过、可安装 | ✅ | ✅ 走 D03 9 步编排 | UI 安装入口、`marketInstallTarget` |
| `CATALOG_CANDIDATES` | 评估过、不可安装 | ❌ | ❌ **查询入口根本找不到** | 仅展示"评估记录/未通过" |

**硬保证（有测试）：** `findMarketEntry()` / `findMarketEntryBySpec()` 只查可安装条目，候选即使被 UI 误传也返回 `undefined`，不会走到 pnpm。

## 2. 数据模型（`packages/spec/src/market.ts`）

新增：

```ts
CANDIDATE_STATUSES = ['needs-review', 'blocked']
CANDIDATE_BLOCKER_CODES = [
  'host-version-incompatible', 'not-a-bundle', 'unverified-publisher',
  'license-restricted', 'install-script', 'closure-not-audited',
  'duplicates-product-scope', 'native-capability-preferred',
  'size-excessive', 'no-declared-compatibility',
]
CANDIDATE_BLOCKING_CODES = [           // 出现其一 ⇒ 必须 blocked
  'host-version-incompatible', 'not-a-bundle', 'license-restricted',
  'duplicates-product-scope', 'native-capability-preferred',
]
```

`CatalogCandidate` 与 `CatalogEntry` 的差异是刻意的：

| 字段 | 可安装条目 | 候选 | 原因 |
|---|---|---|---|
| `compat`（兼容组合 id） | 必填 | **不要求** | 只对已验证组合有意义 |
| `depsClosure`（完整闭包） | 必填 | **不要求** | 没做过完整闭包审计就不能编 |
| `acceptance`（可执行验收） | 必填 | **不要求** | 没实际验收过就没有验收项 |
| `review`（拒绝理由 + 取数事实） | — | **必填** | 否则"为什么不能装"无法复核 |
| `integrity` | 必填 | 必填 | 两边的哈希都来自 registry 真实值 |

`review.facts` 记录评估当时的事实，用来复核判定：

```ts
{ license, unpackedSizeBytes, dependencyCount, peerDependencyCount,
  hasBundlePatch, declaredDshReleases[], hasInstallScript, maintainers }
```

`review.source` 记录 registry URL，`review.evaluatedAt` 记录评估日期，便于重放。

## 3. 策展规则（`packages/core/src/market/curation.ts`）

`collectCandidateProblems()` 把"凭印象拉黑"变成机器可查的不变量：

| # | 规则 | 防的是什么 |
|---|---|---|
| 1 | 含阻断类 code ⇒ `status` 必须 `blocked` | 把明确不可用的写成"再看看" |
| 2 | `blocked` 必须至少有 1 个阻断类 code | 含糊地拉黑，用户不知道原因 |
| 3 | `facts.hasBundlePatch=false` ⇒ 必须有 `not-a-bundle` | 把数据包当插件推荐 |
| 3' | `facts.hasBundlePatch=true` ⇒ 不得有 `not-a-bundle` | 事实矛盾 |
| 4 | `facts.hasInstallScript` ⇒ 必须有 `install-script` | 漏报安装期脚本 |
| 5 | `unpackedSizeBytes > 32 MiB` ⇒ 必须有 `size-excessive` | 体积失控 |
| 6 | 声明兼容列表不含锁定宿主 ⇒ 必须 `host-version-incompatible` | 版本错配却当兼容 |
| 6' | 声明兼容列表**含**锁定宿主 ⇒ 不得判 `host-version-incompatible` | 事实矛盾 |
| 7 | 未声明兼容列表 ⇒ 必须 `no-declared-compatibility` | 兼容性未知却说"没问题" |
| 8 | 候选 `license.redistributable` 必须为 `false` | 未审计闭包却声称可分发包 |
| 9 | 许可为空/`UNLICENSED` ⇒ 必须 `license-restricted` | 许可风险漏报 |
| 10 | 无 `author` 且无 `homepage/repository` ⇒ 必须 `unverified-publisher` | 发布者不可追溯 |
| 11 | id 在「可安装 + 候选」间唯一；同一 `name@version` 不得同时出现 | 双份来源 |
| 12 | 有 `closureAudit` ⇒ 必须有 `depsClosure`、`packageCount` 与长度一致、`verdict` 与现算一致、且不得再标 `closure-not-audited` | 审计结论过期/缺失 |
| 13 | 无 `closureAudit` ⇒ 必须标 `closure-not-audited`；有 `depsClosure` 而无结论 ⇒ 报错 | "有数据没结论" |
| 14 | 闭包结论非 `allowed` ⇒ 必须 `closure-needs-review` 或 `license-restricted` | GPL 等 copyleft 被静默放过 |
| 15 | `installProbe.installed=false` ⇒ 必须 `install-failed`；`true` 却标 `install-failed` ⇒ 事实矛盾 | 装不上却当可用 / 冒充失败 |
| 16 | `installed=true` 但 `listed=false` ⇒ 报错 | "装进去"被当成"可用" |

**测试用反例逐条验证**：把某条规则对应的理由删掉或改掉，`collectCandidateProblems()` 必须报错（27 例里有 14 例是这类反例）。

### 4.1 三条值得单独说的判定

1. **`dsh-zed-acp` 的失败是宿主拒绝的，不是我们猜的**：`dsh plugin add` 直接失败并提示需要
   `allow-version @8kugames/dsh-zed-acp@0.3.9 --dsh-version 0.2.0-rc.2 --accept-risk`。
   这说明它与锁定宿主不是"被接受的组合"——不是许可问题，闭包本身很干净（7 包 MIT/Apache-2.0）。
2. **`dsh-pet` 自己能装上，但这不改变结论**：它的 `dshReleases` 明确不含 `0.2.0-rc.2`（声明性不兼容），
   且闭包含 `@andresaya/edge-tts@1.9.1`（**GPL-3.0-only**）——随我方产物分发会有 copyleft 义务。
   **"能装" ≠ "能分发" ≠ "可用"**，三者在这里正好各差一步。
3. **`dsh-plugin-catalog` 是"列出 ≠ 可用"的活证据**：`dsh plugin add` 成功、`plugin list` 也列出，
   但它 `dsh.bundle.patch` 为空，永远不会挂载。这条同时验证了"已安装"与"已加载"必须分开呈现（PRD §10.4）。

## 6. 真实审计（D11 闭包 + D03 安装探测）

### 6.1 怎么做的

```powershell
# 需要锁定版 dsh 的 bin.js；不给就只做闭包审计（D11）
$env:DDA_AUDIT_DSH_BIN = "<dsh>/lib/bin.js"

# 审计并在仓库内重建 catalog/data/candidate-audits.ts（可复现，不需要额外生成器）
npm run audit:candidates -- --emit-ts=catalog/data/candidate-audits.ts

# 需要原始 JSON 报告时再加 --out
npm run audit:candidates -- --out=%TEMP%\dda-candidate-audit\report.json --emit-ts=catalog/data/candidate-audits.ts
```

- **闭包**：隔离目录 + 真实 `pnpm add --ignore-scripts`（独立 store）→ 遍历已安装 `node_modules` 的依赖图 → 逐包读 `license` → `evaluateClosure()` 现算三态；
- **安装探测**：隔离 `DSH_HOME` + 锁定 `0.2.0-rc.2` → `dsh plugin add <name>@<version>` → 再跑 `dsh plugin list` 核对精确版本；
- **不启动宿主**：`plugin add` 不会加载插件代码（加载发生在 boot），因此本轮不执行第三方插件逻辑；
- 产物：`catalog/data/candidate-audits.ts`（自动生成，40+ 条逐包裁决）。

> 为什么不用 `pnpm licenses list`：它在自定义 store 下会报 `ERR_PNPM_MISSING_PACKAGE_INDEX_FILE`。遍历已安装 `node_modules` 不依赖 pnpm 内部索引，结果同样是"实际装了哪些包"。

**审计带来的结论修正（与上一轮"未验证"对比）：**

| `license.redistributable` | 一律 false（因为没审计） | **仍一律 false**：候选即便闭包 allowed，也还没有业务验收，不视为可分发条目 |

### 6.3 审计发现但**没有**升级为 verified 的原因

`verified` 在本产品里意味着"本机验证过的组合 + 可执行验收项 + 可安装"，三条缺一不可：

1. **没有兼容组合**：`compat.json` 目前只建模 `(dsh, qqbot, node)`，非 QQ 插件无法映射到 `verified-local` 条目；
2. **没有业务验收**：例如"余额挂件是否真的显示正确余额、是否影响宿主布局"需要真机 UI 验证，本轮只到"装进去并能列出"；
3. **没有界面**：D02 未做，候选还无法展示。

因此本轮把证据做扎实，但**不放宽 `verified` 的定义**——这正是 CR-5「未验证条目不得分发/宣称可用」的要求。

## 8. 明确未做（不静默跳过）

1. **D02 插件中心 UI 仍未做**：本轮只交付"候选数据 + 规则 + 审计证据 + 产物"，没有界面。候选在 UI 上的呈现契约已写进本报告 §1（不可安装、不显示安装按钮、单列"未通过"分区），实施时按此执行。
2. **没有升级任何候选为 `verified`**：原因见 §6.3（缺兼容组合建模、缺业务验收、缺 UI）。`needs-review` 的语义仍是"还没验证完"，不是"差不多可以了"。
3. **没有启动宿主做加载验证**：本轮只到 `dsh plugin add` + `plugin list`（不加载插件代码）。真正的"已加载"与"已配置"需要 boot 隔离 profile，属 D02/D03 的后续实测项。
4. **未做全生态普查**：检索命中 200+ 个 `dsh-plugin` 关键词包，本轮只按相关性筛了 7 个。
5. **审计是时点快照**：`review.closureAudit.auditedAt` 记录的是 2026-11-05 的解析结果；依赖升级后需要重跑 `npm run audit:candidates` 并重新生成 `catalog/data/candidate-audits.ts`。
