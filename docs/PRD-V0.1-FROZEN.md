## 1. 产品背景与目标

### 1.1 背景

DeepSeek Harness（`dsh`）是 DeepSeek 官方开源的 Agent 运行环境（MIT，developer preview），能力完整但**面向有开发经验的用户**：需要通过 npm/pnpm 获取、理解 profile 概念、自行配置模型 API、再接入 QQ 等 IM 入口。对普通用户而言，"从零到能在 QQ 里和 AI 对话"仍然是一串高门槛操作。

同时存在三类现实障碍：

| 障碍 | 具体表现 |
|---|---|
| 环境门槛 | 需要 Node.js（≥20.3.0）、pnpm、命令行、profile/插件概念 |
| 网络门槛 | npm / nodejs.org / GitHub 在国内网络下不稳定，用户容易卡在下载环节 |
| 生态门槛 | 插件（尤其 QQ 接入）版本与宿主强耦合；`latest` 常指向预发布；许可状态参差 |

### 1.2 产品目标（V0.1）

| # | 目标 | 判定方式 |
|---|---|---|
| G1 | 普通用户**不需要接触命令行**即可完成 Harness 基础部署 | 3 名无编程经验用户独立完成主流程（§18 验收） |
| G2 | 在**不使用 VPN** 的国内网络下完成核心组件下载与安装 | 断网/弱网与镜像场景实测（§18 验收） |
| G3 | 完成**官方 QQ Bot** 的真实收发 | QQ 真实链路验收（QQ-GATE-01） |
| G4 | 为用户提供**经过验证的**插件资源，而不是"能搜到就能装" | 资源库只含验证通过的组合（§10） |
| G5 | 全程**不污染**用户已有环境、不索取管理员权限、不丢失用户数据 | 隔离与卸载验收（§16、§18） |

### 1.3 非目标（本版本不追求的"好"

- 不做"什么都能装"的通用安装器；
- 不做插件市场的开放生态（不做审核平台、不做评分/评论）；
- 不做模型能力/提示词工程的产品化交付（只做配置引导与少量预制提示词）；
- 不做跨平台（V0.1 仅 Windows x64）。

## 2. 用户画像与核心使用场景

### 2.1 用户画像

| 画像 | 描述 | 关键诉求 | 主要障碍 |

|---|---|---|
| S1 | 全新 Windows 电脑，第一次安装，目标"在 QQ 群里 @ 机器人能回复" | 全程图形界面完成，中途失败可继续 |

## 3. 产品定位与非目标

### 3.1 定位（冻结）

**独立 Windows 桌面软件**，帮助普通用户快速完成 **DeepSeek Harness 环境安装与配置**，并完成 **QQ 接入** 与 **核心插件** 的部署。

一句话：**"清单驱动的部署编排器"**——所有安装动作要么调用官方 CLI/官方发行包，要么"下载 → 校验 → 解压到私有目录 → 仅对子进程注入 PATH"。

### 3.2 非目标（冻结）

| # | 非目标 |
|---|---|
| N1 | **不重新开发 DeepSeek Harness**，不做 Agent 框架、不做模型服务 |
| N2 | **不把 Harness 本体打包进我们的安装包**（一律从官方渠道获取，见 §6） |
| N3 | 不做通用软件管家/包管理器 |
| N4 | 不提供 API 服务、不代理模型请求、不托管用户密钥到云端 |
| N5 | 不做系统级（all-users）安装，不索取管理员权限 |
| N6 | V0.1 **不纳入 SnowLuma**（不下载、不打包、不授权处理、不售卖） |
| N7 | 不修改任何第三方项目源码 |
| N8 | 不做在线插件市场平台（只做策展索引，见 §10） |

### 3.3 边界补充（易被误解的点）

- "不打包 Harness 本体" **不等于**"不让用户一键装"。V0.1 允许软件**代为调用官方渠道**完成安装（B 方案，§6），前提是：用户确认、可解释、可回滚。
- "支持个人 QQ" **不等于**"自动安装任何第三方协议端"。是否自动安装由许可与商业分发条件决定（C 方案，§9）。

## 5. 用户操作流程

### 5.1 主流程（目标路径：全新机器 → QQ 群内可对话）

> 每一步的**界面表达、文案口径、错误提示结构**见 §21「用户体验与交互规范」。

```
① 安装本软件（per-user，无需管理员）
② 打开软件 → 自动检测环境（只读）
③ 选择模式：A 官方群助手 / B 个人陪伴
④ 路线判定结果确认
     ├─ 无 Harness            → CLI 自动化路线
     ├─ 已装 CLI              → 沿用（可选择重装/修复）
     ├─ 已装 Desktop          → 仅引导（不写入其配置）
     └─ 两者并存              → 强制选择（说明互不通用）
⑤ 一键部署（用户确认后执行）
     依赖解析 → Node → pnpm → Harness → web profile → 核心插件
⑥ 配置 API Key（用户自己的 Key）→ 连接测试
⑦ QQ 接入：安装官方插件 → 扫码/填凭据 → 连通性测试
⑧ 在 QQ 群 @ 机器人验证收发
⑨ 完成页：状态总览 + 预制提示词 + 排障入口
```

### 5.2 关键交互规则（需求）

| # | 规则 |
|---|---|
| R1 | 任何"安装/写入"动作前必须有**用户确认**，并说明"将装什么、装到哪、占多少空间" |
| R2 | 每一步都要有**可读的进度与当前状态**；不允许"转圈无信息" |
| R3 | 失败时必须给出：**发生了什么 / 可能原因 / 下一步怎么做**（不是只给错误码） |
| R4 | 用户中断（关软件、断网、重启）后重开，能**一键继续**，不重复已完成步骤 |
| R5 | 任何高风险动作（降级、重置、删除）必须二次确认，并说明后果 |
| R6 | 全流程不要求用户打开终端；确需命令时，以"可复制"形式提供并解释 |

### 5.3 失败与分支流程（需求）

| 情况 | 期望行为 |
|---|---|
| 下载中断 | 保留已下载部分，续传；提示"继续" |
| 哈希不一致 | 丢弃该文件、换源重试、明确告知文件被篡改/损坏 |
| 磁盘不足 | 提前拦截，给出所需空间与清理建议 |
| 权限不足 | 明确提示"本软件不需要管理员；当前操作需要你手动完成 X"（§12） |
| 版本不兼容 | 说明"当前宿主版本 vs 插件声明版本"，不静默降级 |
| 已有 Desktop | 只读展示，拒绝写入，给出官方入口 |

## 6. Harness 安装与管理

### 6.1 安装方式（冻结：B 方案）

**【需求】** Harness 由软件**自动从官方渠道获取安装资源**，**经用户确认后**执行安装；**不将 Harness 本体打包进本软件安装包**。

| 子需求 | 内容 |
|---|---|
| B-1 | 支持自动获取并安装 Harness（Node 运行时 + dsh 包），全程图形界面 |
| B-2 | 安装前展示：来源、版本、体积、安装位置，用户确认后执行 |
| B-3 | 版本**固定到具体版本串**（含预发布），不跟随 `latest` |
| B-4 | 安装后可验证：版本号可读、可启动、可探测可用性 |
| B-5 | 支持升级/降级到**已验证组合**，并可回到上一可用状态 |
| B-6 | 安装位置在用户目录（`%LOCALAPPDATA%`），不写系统目录、不改系统 PATH |

**【技术建议】** 复用官方 CLI 与官方发行包；用 pnpm 完成包安装（M0 实测 npm 不可用，见 §附录 D）。M1 已按此实现。

### 6.2 双路线（CLI / Desktop）

**【需求】** 软件必须能识别 Harness 的两种存在形态，并**分别管理**：

| 路线 | 需求 |
|---|---|
| CLI 路线 | 本软件负责部署、启动、插件安装与配置（V0.1 的标准自动化路线） |
| Desktop 路线 | 本软件**只检测与引导**：展示版本、打开官方入口；**不得代下、代装、不得修改其 profile/凭据** |
| 并存 | 必须提示"两者 profile 互不通用"，要求用户选择其一来管理；禁止混装 |
| 信号矛盾 | 判定为"检测不完整"，**不得猜测后开始安装** |

**【当前实现状态】** 路线四态检测与 `desktop` 只读保护已实现并有单测；**仅 `none`/`cli` 在真机验证过**，"仅 Desktop / 并存 / 矛盾"因缺少官方安装包**未验证**。

### 6.2.1 Desktop 四态的真实环境测试要求（P1，发布前必须完成）

**【需求】** 四个状态必须在**真实安装环境**下逐一验证，不能只在单测里构造：

| # | 状态 | 测试环境准备 | 必须记录的证据 | 通过标准 |
|---|---|---|---|---|
| T-1 | 仅 CLI | 干净系统 + 仅安装 CLI 版 Harness | CLI 版本号、`profiles/` 内容、UI 判定截图 | 判定为 `cli`，且不提示"已检测到桌面版" |
| T-2 | 仅 Desktop | 干净系统 + 仅安装官方 Desktop | 卸载项 `DisplayName`、安装路径、`profiles/desktop`、UI 判定 | 判定为 `desktop`，且**不出现任何安装/写入按钮** |
| T-3 | 两者并存 | 先装 CLI 再装 Desktop | 两套 profile 清单、UI 判定 | 判定为 `multiple`，强制选择且默认标注"互不通用" |
| T-4 | 两者均无 | 干净系统 | 全部检测信号原始值 | 判定为 `none`，且不出现误报 |
| T-5 | 信号矛盾 | 人为构造（如卸载后残留注册表项） | 各信号原始值 + UI 文案 | 判定为 `unknown`，**禁止进入任何写操作** |

**约束**

- 每个状态至少 1 台可还原的虚拟机（或快照）；测试后必须能回到基线。
- Desktop 相关用例在拿到**官方安装包**后方可执行；在此之前 T-2/T-3/T-5 状态记为"未验证"，不得宣称"已支持双路线"。
- 并发场景（Desktop 正在运行）必须单独验证：不得在 Desktop 运行时对同一 `<home>` 执行写操作。

**【当前实现状态】** 仅 T-1/T-4 有真机证据（且 T-1 为本软件私有安装，非用户级 CLI）；T-2/T-3/T-5 **未验证**。

### 6.3 启动与运行

**【需求】** 安装完成后，软件应能启动 Harness 并提供可点击的访问入口；至少能回答"现在到底能不能用"，而不是"进程还在"。

**【技术建议】** 健康判定分级：服务存活 / 鉴权通过 / 业务可用（HTTP 401 只能证明存活）。M1 已实现三级判定并实测达到"可用"。

## 7. 环境检测与依赖管理

### 7.1 检测项（ENV-001/002/003）

**【需求】** 检测结果必须**分状态展示**，并说明"为什么需要它"：

| 检测对象 | 状态枚举 |
|---|---|
| Windows 版本/架构 | 支持 / 不支持（附原因） |
| 磁盘空间 | 充足 / 不足（给出所需空间） |
| 权限 | 普通用户（正常） / 管理员（提示不需要） |
| Node.js | 已安装且满足 / 已安装但版本过低 / 未安装 / 检测失败 |
| pnpm | 同上 |
| Harness（CLI/Desktop） | 见 §6.2 四态 |
| 网络与镜像 | 主源可用 / 仅镜像可用 / 均不可用 |

**【需求】** 检测**只读**，不得因检测而修改任何配置或安装任何东西。

### 7.2 依赖管理原则

| # | 需求 |
|---|---|
| D-1 | **已有可用环境优先复用**，不重复安装（避免版本冲突） |
| D-2 | 自管运行时安装到私有目录，**仅对子进程注入路径**，不改用户环境 |
| D-3 | 按需安装：不使用的组件不下载、不占空间 |
| D-4 | 每个组件的安装都要可验证（版本、可执行性），验证失败即视为未完成 |
| D-5 | 版本下限取**所有组件的最严要求**（例：QQ 插件要求 Node ≥ 20.3.0） |
| D-6 | **复用已有 Node 的前提条件**：①版本满足全部组件下限（当前 ≥ 20.3.0）②`node -v` 可正常执行 ③路径稳定（非临时目录/非版本管理器临时切换）④不要求写入权限；四条同时满足才复用 |
| D-7 | **不满足 D-6 时一律使用私有运行时**：安装到本软件数据目录、仅对子进程注入 PATH；**不升级、不卸载、不修改**用户已有 Node |

**复用与私有运行时的策略（P1，需求）**

| 用户机器状态 | 产品行为 |
|---|---|
| 无 Node | 安装私有 Node（默认路径） |
| 有 Node 且满足下限且通过 D-6 校验 | **优先复用**；在 UI 中显示"使用系统已有的 Node x.y.z"并可切换为私有 |
| 有 Node 但版本过低 / 损坏 / 路径不稳定 | 安装私有 Node，并在确认页说明"不会动你已有的 Node" |
| 有多个 Node（nvm 等版本管理器） | 默认**不复用**（路径随会话变化），改用私有运行时；如需复用必须由用户显式指定 |
| 用户主动选择"隔离模式" | 无论是否存在系统 Node，都安装并使用私有运行时 |

**约束**

- 私有运行时目录可整体删除即回收；删除不得影响系统 Node。
- 复用系统 Node 时若后续出现依赖缺失/原生模块不兼容，应能一键切换到私有运行时（反之亦然）。
- **不允许**为复用而修改系统 Node 的安装（例如补装全局包、改 `npm config`）。

**【当前实现状态】** D-1/D-2/D-4/D-5 已实现（Node/pnpm/dsh）；D-3 仅在上述三项上生效，Python/FFmpeg/Git 等适配未实现。

### 8.4 两种绑定方式必须分别验证（P1）

**【需求】** 官方 QQ 接入存在两种凭据获取方式，二者**不得合并为一项验收**：

|---|---|---|---|---|
| **A. AppID + AppSecret** | 用户在开放平台创建机器人后填入凭据 | 安全存储、注入运行环境、触发连接 | 凭据注入是否生效、机器人是否上线、收发是否正常 | **待验证** |

**约束**

- 两种方式的验证证据必须分开记录（截图/日志/时间），不得用 A 的结果替代 B。
- 若实测发现插件只支持其中一种，必须在 PRD 与 UI 中如实标注"当前仅支持 X 方式"，并记录为待确认事项（U12）。
- 不得为了让流程"看起来完整"而伪造另一种方式的入口。

### 9.4 个人 QQ 完整用户引导流程（P1）

**【需求】** 用户选择"个人 QQ"后，必须能走完下面这条**不依赖命令行**的引导链（每一步都要有"我在哪、下一步去哪"的明确指示）：

```
   ├─ 展示组件名称/版本/许可/来源 → 用户确认

④ 引导安装（默认路径）

⑤ 装后检测（PQ-4）

   ├─ 是否在运行（进程/端口）

⑦ 收发验证（人工确认 + 可选自检）
   └─ 未完成 → 标记"未验证"，不得显示"可用"
⑧ 完成/排障页
   └─ 状态总览 + 常见失败（未启动/端口占用/协议端版本不符）+ 重新检测入口
```

## 10. 插件资源库与国内下载

### 10.1 规模（冻结：A 方案）

**【需求】** V0.1 **只提供经过验证的核心插件套装**，不追求数量；每个进入清单的插件都必须具备可复现的验证记录。**核心清单见 §10.5**（含承载方式与验证状态，明确"哪些能力不是插件"）。

### 10.2 插件元信息（必需字段）

| 字段 | 说明 |
|---|---|
| 名称/标题/描述 | 支持中英 |
| 作者/主页/仓库 | 可追溯 |
| 版本与发布时间 | 精确版本，禁止 `latest` |
| 兼容范围 | 宿主版本区间 + 已知可用组合 |
| 来源 | npm（含 registry）或 git（固定 commit） |
| 完整性 | 哈希/签名 |
| **许可证** | SPDX + 是否允许再分发/商用 |
| **验收方式** | 如何证明"装上并可用"（可执行的检查项） |
| 依赖闭包 | 必须包含必要依赖，且逐项过许可门禁 |

### 10.3 国内下载（冻结：需求 7）

**【需求】** 在不使用 VPN 的情况下，用户应能获取受支持的插件与运行时。为此采用**三层下载优先级**，并对每一层施加同一套校验与许可约束：

| 层级 | 来源 | 角色 | 使用条件 |
|---|---|---|---|
| **L1** | **我方维护的国内资源库**（对象存储 + CDN，只做镜像转发） | 首选：解决可达性与速度 | 仅存放**许可允许再分发**的产物；逐对象记录上游 sha256 |
| **L2** | **可信公共镜像**（如 npmmirror 及其二进制镜像） | 次选：L1 未覆盖或 L1 故障时 | 必须与上游哈希一致；不一致即视为不可信 |
| **L3** | **官方下载源**（官方 npm registry、官方发行地址） | 兜底：最终事实来源 | 始终可用；哈希以清单为准 |

**贯穿三层的硬性要求**

| # | 需求 |
|---|---|
| CN-1 | 按 **L1 → L2 → L3** 顺序尝试；任一层成功后不再尝试后续层；失败自动回退并记录原因 |
| CN-2 | **资源版本锁定**：所有资源以精确版本 + 内容哈希固定，禁止 `latest`/范围解析；同一组合在三层中的版本必须完全一致 |
| CN-3 | **SHA-256 强制校验**：以清单中的哈希为唯一标准，镜像自述/HTTP 头一律不作依据；不一致立即丢弃并换层重试 |
| CN-4 | **依赖闭包完整**：插件必须携带其必要依赖（逐项列明版本与许可），不得假设"运行时再去装" |
| CN-5 | **许可证审核**：进入 L1/L2 的每个包（含传递依赖）必须通过 §12.1 判定；`UNLICENSED`/禁止再分发者**不得进入 L1**，也不得镜像 |
| CN-6 | **资源缓存与失败回退**：本地内容寻址缓存；缓存命中须重新校验哈希；缓存损坏自动淘汰；离线/本地导入受许可约束 |
| CN-7 | **索引可达性**：索引本身也必须能从 L1/L2 拉取，或随包内置；索引获取失败不得导致"整页空白" |
| CN-8 | 断点续传与有限次重试；失败后给出可执行的下一步（换层/检查网络/使用离线包） |

**【状态与口径约束（重要）】**

- **资源服务器的责任方、成本与运营方案属于待确认事项（U5）**，当前无归属、无预算、无 SLA。
- 因此：**在资源服务器未落地前，不得对外宣称"无 VPN 全流程已实现"**；只能表述为"支持镜像优先与官方源兜底，国内可达性依网络环境而定"。
- 已完成的验证仅限于"官方源 + 公共镜像 + 哈希/续传"的技术链路（见 §附录 D），**不等于 L1 已建成**。

### 10.4 状态呈现（五段证据）

**【需求】** 必须区分：**已解析 → 已下载 → 已安装 → 已配置 → 已连通**。禁止"下载完成 = 部署成功"。

**【当前实现状态】** 插件安装与"已安装"判断已实现；五段中的"已配置"未实现、"已连通"对官方 QQ 而言受 **QQ-GATE-01** 门禁约束（未通过前不得显示为"可用"）；资源中心（索引/详情/国内三层映射/离线）整体**未实现**。

## 11. API 配置引导

### 11.1 端到端流程（需求，必须全链路可用）

```
① 用户自备 API Key
   └─ 明确告知：软件不提供、不转售、不代理 API；Key 由用户自行申请并自行承担费用
② 本地输入
   ├─ 掩码输入框（默认不可见，可切换显示需二次确认）
   └─ 本地格式校验（长度/前缀/字符集），**不联网**、不因格式错误发起请求
③ 本机加密存储（DPAPI）
   ├─ 仅主进程可解密；渲染层只能拿到掩码（如 sk-****abcd）
   └─ 明文不落盘、不进日志、不进诊断包
④ 安全写入 Harness 配置
   ├─ 只使用**官方文档化**的配置方式；写入前备份原配置
   ├─ 写入后回读校验（能否被宿主识别）
   └─ 不猜测字段名/层级；未验证的写入方式一律不做（见 §11.4）
⑤ 真实连接测试
   ├─ 用用户的 Key 发起一次**最小真实请求**（非本地假校验）
   ├─ 记录：HTTP 状态、耗时、模型名（如返回）、错误码
   └─ 绝不把 Key 或完整请求头发往我方服务器
⑥ 结果分类与可执行建议（见 11.2）
⑦ 密钥修改 / 删除
   ├─ 修改：重新走 ②③④⑤
   └─ 删除：清除本机密文 + 回滚/清除 Harness 侧配置 + 提示"已删除"
⑧ 日志与诊断包脱敏
   └─ 已知字段名（apiKey/secret/token/authorization）+ 已知密钥值双重替换
⑨ 全程不经我方服务器
   └─ 无遥测、无上报；网络请求只指向用户配置的模型服务与安装源
```

### 11.2 连接测试的错误分类（需求）

| 分类 | 判定依据（需实测确认） | 用户可见提示与下一步 |
|---|---|---|
| 成功 | 最小请求返回 2xx | "连接成功（耗时 X ms，模型 Y）" |
| 鉴权失败 | 401/403 | "Key 无效或无权限：请确认 Key 来源与权限，重新粘贴" |
| 配额/余额 | 429 或明确的配额错误码 | "额度不足或触发限流：请到服务商控制台确认余额/限额" |
| 网络不可达 | DNS/连接超时/TLS 失败 | "无法连接模型服务：检查网络/代理；企业网络可能拦截" |
| 服务端错误 | 5xx | "服务端暂时不可用：稍后重试，或换用其他可用模型" |
| 配置未生效 | 本地回读不到写入结果 | "配置未写入成功：请在 Harness 界面中手动粘贴（附步骤）" |
| 未知 | 其他 | "请求失败（错误码 X）：已写入日志，可导出诊断包" |

> 具体状态码到分类的映射**需实机联调确认（U2）**，本表只定义产品必须覆盖的类别，不虚构接口。

### 11.3 密钥生命周期（需求）

| 场景 | 必须做到 |
|---|---|
| 首次设置 | 加密保存 + 写入配置 + 连接测试 |
| 修改 | 覆盖旧值；旧值不残留（含备份） |
| 删除 | 本机密文删除 + 宿主侧配置清理 + 二次确认 |
| 导出/迁移 | **不提供**明文导出；如需换机，要求重新输入 |
| 诊断包 | 永不包含密钥；脱敏规则有单测 |
| 软件卸载 | 明确询问是否保留密钥（默认删除本机密文） |

### 11.4 配置写入边界（重要，禁止假设）

**【需求】** API Key 写入 Harness 的方式必须满足：

| # | 要求 |
|---|---|
| CFG-1 | 只使用**官方文档化**的配置途径（CLI/设置页/公开配置文件格式） |

| CFG-4 | 任何写配置动作都必须先备份、可回滚；不得覆盖用户的其它配置项 |

## 13. 动态依赖安装机制

**【需求】** 安装顺序**由组件依赖关系动态决定**，不写死固定顺序；同时必须满足：

| # | 需求 |
|---|---|
| DY-1 | 组件声明明确的前置依赖（例如"启动 dsh 需要 Node"、"QQ 插件需要宿主 + profile"） |
| DY-2 | 按依赖拓扑排序执行；无依赖关系的组件不应被强加顺序 |
| DY-3 | 每一步幂等：已满足即跳过（重复点击"安装"不产生第二次安装） |
| DY-4 | 失败即暂停，保留已完成步骤；可从第一个未完成步骤继续 |
| DY-5 | 回滚只撤销**本次任务创建**的产物，绝不动用户原有内容 |
| DY-6 | 同一时刻只允许一个部署任务在跑（避免并发写同一目录） |

**【技术建议】** 用"步骤 + 前置条件 + 回滚"的 Plan/Step 模型实现；M1 已按此实现（13 步、幂等、可恢复）。**DY-2 的"动态"目前体现为步骤的依赖前置条件与顺序，尚未实现由外部清单驱动的通用依赖图**。

| QG-2 | 门禁未通过时，**不允许**在任何对外文案、商店页、售卖页、演示中宣称"官方 QQ 已完整可用/已支持收发" |
| QG-3 | **不允许**用 Mock、假机器人、回环消息、截图伪造等方式替代真实收发验收 |

### 18.3 发布门禁与豁免规则

**门禁分级**

| 级别 | 含义 | 能否豁免 |
|---|---|---|
| **G-A 不可豁免** | 违反即不得发布（无论谁批准） | **否** |
| **G-B 需书面决策** | 需产品负责人书面确认并记录风险 | 可，但必须留痕 |
| **G-C 常规** | 由发布负责人按清单核对 | 可，记录即可 |

**G-A 不可豁免清单（安全与核心链路）**

| # | 项目 | 判定 |
|---|---|---|
| G-A1 | 密钥不泄露：明文不落盘、不进日志/诊断包、不回传渲染层、不上传 | 任一违反即阻断 |
| G-A2 | 不删除用户数据：卸载不删用户数据、回滚只删本次创建 | 任一违反即阻断 |
| G-A3 | 安装不索取管理员权限、不写系统级配置 | 违反即阻断 |
| G-A4 | 下载/解压安全：强制哈希校验、拒绝 zip-slip/符号链接逃逸 | 任一缺失即阻断 |
| G-A5 | 真实 QQ 核心链路（A6）**若对外宣称 QQ 能力**，必须通过 QQ-GATE-01 | 未通过则不得宣称（见 QG-2/QG-4） |
| G-A6 | 核心部署链路（A3）失败无恢复手段 | 阻断 |
| G-A7 | 许可证合规：不得分发 `UNLICENSED`/禁再分发组件 | 阻断 |
| G-A8 | 若启用远程清单/索引，则必须满足 SEC-9/SEC-10（签名 + 防回滚） | 阻断 |

**G-B 需书面决策清单**

| # | 项目 | 决策要求 |
|---|---|---|
| G-B1 | A1 仅 Win10 通过、Win11 未验证 | 产品负责人书面确认发布范围（如"仅标注支持 Win10"） |
| G-B2 | A9 在 L1 资源库未落地时发布 | 必须同时修改对外文案：不得宣称"无 VPN 全流程可用" |
| G-B3 | 代码签名缺失（SEC-7） | 必须标注"未签名"，并接受 SmartScreen 拦截预期 |
| G-B4 | A5/A7/A8/A12 未达标 | 逐项说明影响与替代方案 |
| G-B5 | A14 未完成三人测试 | 需给出替代验证与风险接受人 |

**G-C 常规清单**：已知问题清单公开、版本号/发布说明、第三方声明随包、回滚说明。

**优先级与门禁的关系（重申）**：P0 未完成 = 不能发布；P1 未完成 ≠ 可以忽略——P1 若属于 G-A（如密钥保护、QQ 真实链路），同样阻断；其余 P1 走 G-B 书面决策。

## 21. 用户体验与交互规范

> **目标用户是没有编程基础的普通 Windows 用户。** 他们不需要、也不应该被迫理解 npm / pnpm / profile / 依赖闭包 / 哈希等术语才能完成安装。

### 21.1 总体原则

| # | 原则 |
|---|---|
| UX-1 | **术语零门槛**：界面只出现"运行环境""插件""接入 QQ"等日常词；技术名词只出现在"查看详情"里 |
| UX-2 | **一屏一件事**：每屏只问一个问题/只做一个决定 |
| UX-3 | **永远知道下一步**：任何界面都有明确主按钮；失败界面也有"下一步"而不是死路 |
| UX-4 | **不惊吓**：不出现红色大字报式报错；错误用"发生了什么+怎么办"陈述 |
| UX-5 | **可反悔**：安装前可取消；高风险动作二次确认；中断可继续 |
| UX-6 | 全流程**不要求打开终端**（§5.2 R6） |

### 21.2 首页与部署状态

| 元素 | 规范 |
|---|---|
| 首屏结论 | 一句话："你的电脑可以安装 / 还缺 X / 已安装且可用" |
| 状态卡 | 3 个：运行环境、Harness、QQ 接入；每卡显示"可用/需处理/未开始" |
| 主按钮 | 只有一个（下一步）；其余为次要操作 |
| 长任务入口 | "继续上次安装"在有未完成任务时置顶显示 |

### 21.3 环境检测

- 检测过程**只读**，界面明确写"这一步不会修改你的电脑"。
- 每项结果用**人话**：`Node.js` → "运行环境（必需）"；版本不符 → "版本偏旧，需要更新（不会动你原来的）"。
- 检测失败允许"重试"与"跳过（不推荐）"，并说明跳过的后果。

### 21.4 安装确认

确认页必须回答 4 个问题：**装什么、装到哪、占多大、要多久**；并明确"可以随时取消，取消不会留下垃圾"。

### 21.5 下载进度

- 显示：当前步骤名（人话）+ 百分比 + 已下载/总量 + 剩余时间估计（可为区间）。
- 网络慢/失败时给出"正在尝试备用下载源（第 2 个）"，而不是静默等待。
- 提供"暂停/继续"（V0.1 最低：允许关闭后继续）。

### 21.6 API 配置

- 输入框默认掩码；提供"从哪里获取 Key"的**可点击指引**与截图/步骤。
- 保存后**立即测试**，用三句话说明结果：状态（成功/失败）、原因（人话）、下一步（做什么）。
- 明确写"Key 只保存在这台电脑上，不会上传"。

### 21.7 QQ 接入

- 先让用户选路线（官方机器人 / 个人 QQ），并**在两句话内**说明区别与可行性。
- 官方路线：给出"扫码"与"填 AppID/AppSecret"两条路，标注哪条更简单。
- 绑定成功后显示"已连接（最近心跳 X 秒前）"，未完成则显示"待完成：还需扫码"。
- **不得**在未通过门禁时显示"QQ 已可用"。

### 21.8 插件资源库

- 只展示策展清单；每项显示：一句话用途、是否已验证、许可提示（如需人工安装会明确标注）。
- 安装按钮旁显示"将安装 X MB / 预计 Y 秒"。
- 安装后用**三态徽标**：已安装 / 待配置 / 已连通；不使用"成功"这样含糊的词。

### 21.9 错误提示

统一结构（禁止只给错误码）：

```
标题：一句人话说明发生了什么
原因：可能的原因（1–3 条，按可能性排序）
下一步：一个主按钮 + 一个次要入口（查看详情/导出日志）
```

### 21.10 恢复操作

| 场景 | 入口 |
|---|---|
| 安装中断 | 首页置顶"继续上次安装" |
| 安装失败 | 失败卡片内"重试这一步"（不重跑全部） |
| 装坏了 | 设置内"恢复到上一可用状态"（二次确认 + 说明影响） |
| 想重来 | "重置安装"（二次确认，明确只删除本软件创建的内容） |

### 21.11 完成页面

- 一句话结论 + 三个状态卡（环境/Harness/QQ）。
- 主按钮："打开 Harness"；次要："去 QQ 群试试"（附如何 @ 的说明）。
- 提供"生成一句话分享/求助文本"（不含任何密钥），方便用户求助。
- 明确列出"还没完成的项"（如 QQ 未验证），不隐藏。

### 21.12 可访问性与本地化（V0.1 最低）

- 支持 100%/125%/150% 缩放不破版；键盘可达主要操作（Tab + Enter）。
- 中文为默认语言；不要求 V0.1 提供多语言。
- 颜色不作为唯一状态标识（同时用文字/图标）。
