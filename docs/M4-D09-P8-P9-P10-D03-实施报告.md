## 1. D09 首批资源策展

### 1.1 验收方式改为可执行结构

之前 `acceptance` 是一组字符串，"群内 @ 机器人并收到回复"这类描述无法判定是否真的执行过。现在（[packages/spec/src/market.ts](../packages/spec/src/market.ts)）：

```ts
{ id: 'acc-group-reply', step: '在已授权的群里 @ 机器人发送一条文本', evidence: '群里收到机器人对这条文本的文字回复' }
```

- `id` 必填且 `acc-<slug>`，条目内唯一；
- `step` 是**用户做的一步**，`evidence` 是**可观测到的结果**，两者都不能是空话（schema 强制长度，测试断言 `step !== evidence`）。

### 1.2 新增的策展规则（`collectCatalogProblems`）

| 规则 | 为什么 |
|---|---|
| `license.spdx` 必须等于闭包内同名包（本体）的许可 | 条目不得宣称与包事实不同的许可 |
| `verified` 条目必须有 `author` | PRD §10.2「作者/主页/仓库：可追溯」 |
| `verified` 条目必须有 `homepage` 或 `repository` | 同上 |
| 验收项 id 条目内唯一 | 否则 D02 无法按 id 定位证据 |
| `engines.dsh` 必须锁成 `=<compat.dsh>` | 索引只能宣称本机验证过的组合（D01 已有，本轮补测试） |

### 1.3 内容与许可快照

- V0.1 仍然只有 **1 个真插件**（`@tencent-connect/dsh-qqbot@0.5.5`），不扩充；
- 闭包快照 37 包，按许可分布 MIT 26 / ISC 8 / Apache-2.0 1 / Python-2.0 1 / UNLICENSED 1，与前置验证 §5.2 完全一致；
- overlay 里的逐包裁决 == `evaluateClosure()` 现算结果（测试逐字段比对），`redistributable=false` 与"闭包含 UNLICENSED"一致。

### 1.4 测试（`tests/core/catalog-curation.test.ts`，13 例）

范围 1 + 必需字段 3 + 可执行验收 2 + 许可一致性 4 + schema 强校验 3。

## 2. P-8 registry 回退

### 2.1 根因（两条链路，两个不同问题）

| 链路 | 事实 | 后果 |
|---|---|---|
| 我们调用的 `dsh plugin add`（CLI） | CLI 只把 `--registry=` 转发给 pnpm，**自身没有 registry 计划**（源码核对 `dsh-plugin-manager/operations`） | 镜像挂了就直接失败，不会问官方源 |
| Harness 插件服务的 `registryPlan()` | 只有"pnpm 自身 registry 是官方源**或**在 fallback 列表里"才把它算进集合；`container.ts` 把 `npm_config_registry` 固定成镜像，且 profile 未配 fallback → 集合只剩镜像 | 服务路径的官方回退同样失效 |

### 2.2 修复

1. **[packages/core/src/market/registries.ts](../packages/core/src/market/registries.ts)**
   - `registryPlan()`：L2 镜像 → L3 官方（L1 未落地，不虚构）；
   - `isRegistryRetryable()`：只在"换源可能有用"的失败上回退（5xx/404/无匹配版本/连接类），**认证与版本错误不回退**；
   - `installWithRegistryFallback()`：逐层安装，全部失败时错误消息列出两层各自原因。
2. **[packages/core/src/market/registry-config.ts](../packages/core/src/market/registry-config.ts)**
   - 往 profile `cordis.patch.yml` 写受管块：`plugin-manager { registry: npmmirror, fallbackRegistries: [npmjs] }`；
   - 幂等、保留用户条目/注释、可回读、可移除；`isRegistryFallbackConfigured()` 用来做写入后自检。
3. **适配器**：`DshCli.addPlugin(profile, spec, { registry })` → 追加 `--registry=<url>`。
4. **部署计划新增步骤 `configure-registry`**：在 `ensure-profile` 之后写入配置并回读断言，日志打印 `镜像 → 兜底 官方`。
5. **所有安装入口**都改走 `installWithRegistryFallback`（部署计划、`HarnessService`、D03 编排器）。

> 文案口径：只说"镜像优先、官方兜底"，不承诺"全部走国内镜像"。

### 2.3 测试

- `tests/core/registries.test.ts`（6）：计划顺序、可回退判定、单源成功、镜像失败换源、认证失败不回退、双层失败消息。
- `tests/core/registry-config.test.ts`（6）：写块、幂等、不破坏用户条目、回读判定、"只有镜像无兜底"判为未生效（复现现网缺陷）、移除。

## 3. P-9 `downloadVerified` 错误码

**问题：** 循环结束后统一抛 `E_DOWNLOAD_NETWORK`，即使真实原因是哈希不一致（`E_HASH_MISMATCH` 在循环里被 `break` 后丢失）。用户看到"检查网络"，实际是源内容被篡改。

**修复：** 记录每次失败的 `ErrorCode`；最终抛出时：
- 出现过 `E_HASH_MISMATCH` → 抛 `E_HASH_MISMATCH`，hint 明确"内容与清单不一致，已删除损坏文件"；
- 否则用最后一次的具体错误码（如 `E_DOWNLOAD_HTTP`）；
- 都没有才回落到 `E_DOWNLOAD_NETWORK`。

**测试**（`tests/core/downloader.test.ts`，8 例）：原"哈希不一致应报网络错误"的断言改为 `E_HASH_MISMATCH`（该断言本身锁住了缺陷）；新增"全 404 → `E_DOWNLOAD_HTTP`""一个源篡改 + 一个源不可达 → 仍报哈希不一致"。

## 4. P-10 安装入口收敛（Gate 4 ⑤）

**问题：** `harness-service.installQqPlugin()` 与 `installPlugin(spec)` 直接把 spec 交给 pnpm，不经过 `assertCombination`。

**修复：**

| 入口 | 现在 |
|---|---|
| 部署计划 `install-qqbot` | 已有 `assert-combo` 步骤 **+** 调 D03 编排器（第 1 步即 compat） |
| `HarnessService.installQqPlugin()` | `assertPluginInstallAllowed`（精确 spec + catalog 白名单 + verified-local 组合）+ `assertDistributionAllowed` + 编排器 |
| `HarnessService.installPlugin(spec)` | **删除**。改为 `installAdapterPlugin()`，只装 `PERSONAL_QQ_ADAPTER.spec`（`@dda/spec` 单一来源），仍受白名单 + 同一 registry 回退约束 |
| 适配插件常量 | 从 `personal-qq-service` 上移到 `packages/spec/src/qq-personal.ts`，避免两处各写一个版本号 |

**`assertPluginInstallAllowed()` 的硬规则**（[packages/core/src/market/install-policy.ts](../packages/core/src/market/install-policy.ts)）：
- 只接受精确 `name@version`；`latest`、范围、git、本地路径、带额外参数的字符串一律拒绝；
- 官方插件必须在 catalog 白名单内**且**命中 `verified-local`；
- 适配插件只认显式适配白名单（它不属于 compat 的三元组）。

**测试**（`tests/core/install-policy.test.ts`，12 例）覆盖上述全部拒绝/放行分支。

> Gate 4 ⑤ 的判定：**码级已收敛（含单测）**；未做"真的去装一个非法组合"的端到端（会改动用户 profile，且没有新增信息）。

## 5. D03 安装编排

### 5.1 9 步流水线（[packages/core/src/market/install-plan.ts](../packages/core/src/market/install-plan.ts)）

| 步 | 动作 | 可重试 | 缺证据时 |
|---|---|---|---|
| 1 | compat 白名单（**先于任何 pnpm 调用**） | 否 | — |
| 2 | 预检（profile 可写等） | 是 | — |
| 3 | 解析 spec（`marketInstallTarget`） | 否 | — |
| 4 | registry 计划 | 是 | — |
| 5 | 执行 `dsh plugin add`（逐层换源） | 是 | — |
| 6 | 安装复核（`plugin list` + profile 依赖） | 是 | — |
| 7 | 加载复核（`--dump-config` 出现该 bundle 且未 disabled） | 是 | `unverified` |
| 8 | 配置自检（字段存在且格式合法） | 是 | `unverified` |
| 9 | 连通探测 | 否 | `unverified` |

- 错误消息形如 `第 5 步（install）失败：…`，**只重试该步**；非可重试步只尝试一次。
- 第 7–9 步没有证据源时记 `unverified`，**绝不记 succeeded**（对应 PRD §10.4"未验证不得显示成功"）。
- `outcome.steps` 就是可回放的执行记录（步号、状态、尝试次数、明细）。

### 5.2 与官方 `marketInstallTarget()` 等价位

本地实现 npm → `name@version`（带 registry 覆盖时附带该字段）、git → `git+<url>.git#<commit>[&path:/dir]`，测试直接 import 官方函数逐字段比对（npm / npm+registry / git+子目录三组）。

### 5.3 peerDeps 缺失的可读原因

`explainInstallFailure()`：识别 `ERR_PNPM_PEER_DEP_ISSUES` / missing peer，抽取 `@deepseek-ai/*` 包名，输出
"…需要的宿主包没有满足：@deepseek-ai/xxx。这些包由 Harness 本体提供，不会装进 profile；出现该错误通常说明宿主版本与插件不匹配。"
并以 `E_VERSION_UNSUPPORTED` 抛出，hint 指向升级宿主或换已验证版本。

### 5.4 测试（`tests/core/install-plan.test.ts`，16 例）

对应验收 5 条：① 非白名单组合第 1 步被拒（且无安装调用）② 每步失败含步号、按步重试（单源重试 / 双源换源两种路径都覆盖）③ 镜像 503 → 官方成功 ④ peerDeps 可读原因 ⑤ 成功路径 + 7–9 步 `unverified` + disabled 时第 7 步失败。
