## 3. 安全模型（与 M3.1 同一套）

| 项 | 做法 |
|---|---|
| 凭据落盘 | 仅 `secrets.bin`（Windows DPAPI 密文，键 `qq.appId` / `qq.appSecret`），无明文 |
| 凭据注入 | 启动 `dsh` 时作为 `QQBOT_APPID` / `QQBOT_SECRET` 环境变量注入；profile 只写 `__FROM_ENV__` |
| 前端可见 | AppID（非机密）+ AppSecret 掩码（`abc****wxyz`）；完整 secret 永不出主进程 |
| 日志 / 诊断 | 不记录凭据；状态证据只保留插件输出中的非机密行；扫码链接里的 `task_id` 在展示时脱敏 |
| 扫码（决策 D1） | 走插件自带的官方流程；成功后**插件自己**把 appId/appSecret 明文写入 profile，UI 显著警示（黄条），并提供「迁移到加密存储」（决策 D2）强制清掉明文 |
| 打开链接 | 主进程校验 host 必须是 `q.qq.com`，不做任意 URL 转发 |
| 无协议逆向 | 未实现任何 QQ 协议、未代替用户登录、未绕过风控 |

## 4. 配置写入机制（关键约束）

`im-qqbot` 由插件 bundle patch `insert` 提供，我们的 profile 层用同 id 覆盖。受控实验证明：**覆盖是整体替换 `config`**，所以我们**写全**所有相关字段（`appId/appSecret/requireMention/groupPrompt/directPrompt/streaming/textChunkLimit/historyLimit/access/media/sendFile`）。省略任何字段都会退回 schema 默认值（例如 `streaming=true`）。

实际写入结果（真实实例）：

```yaml
# >>> dda:managed:qq:begin  (…)
- id: im-qqbot
  config:
    appId: __FROM_ENV__
    appSecret: __FROM_ENV__
    requireMention: true
    streaming: true
    textChunkLimit: 4500
    historyLimit: 10
    access: { c2cMode: open, c2cAllow: [], groupMode: open, groupAllow: [] }
    media: { enabled: true }
    sendFile: { restrictPaths: true }
# <<< dda:managed:qq:end
```

`dsh --profile web --dump-config` 回读确认同样的值出现在组合结果里（`verify()` 通过才返回成功，否则自动回滚）。

## 5. 状态机（M3.2-03 的落地）

| 相位 | 判定依据（缺一不可） |
|---|---|
| `not-deployed` | `harness/<ver>/…/dsh/lib/bin.js` 不存在 |
| `not-installed` | 插件不在 `dsh plugin list` |
| `version-mismatch` | 版本 ≠ `BASELINE.qqbot.version` |
| `installed` | 插件在、Harness 未运行 |
| `unbound` | Harness 在跑、无凭据、且没有扫码链接 |
| `binding` | Harness 在跑、无凭据、stdout 出现官方 q.qq.com 链接 |
| `connecting` | 有凭据（DPAPI 或 profile 明文）、未就绪且未超时（90s） |
| `connected` | stdout 出现 `[im-qqbot] Bot ready! appId=…` |
| `reconnecting` | 最近一次事件是 `Bot disconnected … reconnecting` |
| `failed` | `permanently … giving up` / `Bot start failed` / 有凭据但 90s 未就绪 |

「状态依据」把上述每一行原文（脱敏后）展示给用户，避免"看起来连上了"的误导。

## 6. 异常恢复（决策 D4：不自动重启）

| 场景 | 行为 |
|---|---|
| 网络断开 | SDK 自动重连（WS `RESUME` + 退避）；UI 显示"重连中（无需重新扫码）" |
| QQ 服务端/凭据错误 | 显示"连接失败"并给出「检查 AppID/AppSecret 是否属于同一机器人」的下一步 |
| Harness 进程退出 | 不自动重启；第 2 节可一键重启，凭据从 DPAPI 重新注入（方式 A 无需重新授权） |
| 桌面助手重启 | 下次启动 Harness 时自动重新注入（DPAPI 读取），免重新扫码（方式 A） |
| Windows 重启 | 本版本**没有开机自启**，需用户打开助手后启动 Harness；此点已在已知问题登记 |

## 7. 与 M3.1 的关系（回归保障）

- `HarnessService` 的注入环境改为合并函数（`api.launchEnv()` + `qq.launchEnv()`），API Key 的键（如 `DEEPSEEK_API_KEY`）与 QQ 的键（`QQBOT_*`）互不覆盖。
- 受管块拆成两个命名 section，QQ 的写入/删除不会动 `llm-deepseek`、`agent-default-model`、`ui-settings-general`（测试断言 + 实机 patch 检查）。
- 现有 132 项测试全绿（现为 161 项），M3.1 的真实 Key 调用能力未受影响（实机 `apiStatus.configured=true`）。
