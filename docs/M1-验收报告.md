## 3. 关键结论（与 M0 的关系）

1. **基线落实**：Node 22.23.4 / pnpm 11.28.5 / dsh 0.2.0-rc.2 / qqbot 0.5.5 / profile `web` —— 全部与 M0 结论一致；`0.1.0-rc.8` 在 `compat.json` 中标为 `blocked`，代码路径无法选中。
2. **npm 未被使用**：整个部署链路只调用 pnpm（M0 的 npm 挂起问题被结构性规避）。
3. **健康判定没有夸大**：无 token 时只报 `alive`(401)，带 token 且拿到应用外壳才报 `usable`。
4. **隔离成立**：所有运行时、profile、harness 都在 `%LOCALAPPDATA%\DeepSeekDeployAssistant` 下；测试后 `~/.dsh` 仍不存在。
5. **卸载语义正确**：卸载后注册项清除、部署数据（harness/profile）保留。

## 4. QQ-GATE-01 状态

```
QQ-GATE-01  未通过
已验证  ：插件安装、插件加载、绑定二维码/链接生成
未验证  ：真实扫码授权、群/私聊消息收发、图片消息、断线重连、重启后免扫码恢复
Mock 范围：安装流程 + UI 状态机（使用真实包与真实进程，但无真实聊天对端）
```

**为什么不能算通过**：本轮所有验证止于"进入扫码绑定"。真实收发需要①可用的 QQ 机器人（`appId`/`appSecret` 或手机扫码授权）②真实群/私聊对端，二者在测试环境中都不存在；按任务约束，不得绕过官方授权，也不得以模拟替代验收。

**解除条件**（需产品/运营提供）：
1. 一个可用的 QQ 机器人凭据，或一台可扫码手机；
2. 一个测试群与一个私聊对端；
3. 验收脚本：扫码 → 群 @ 回复 → 私聊 → 发图 → 断网 30 s 重连 → 重启应用后免扫码恢复。

## 5. 冻结定位的遵守情况

| 约束 | 结论 |
|---|---|
| 不重开发 Harness | 遵守（只调用 CLI） |
| 不打包 Harness 本体 | 遵守（从镜像/官方在线安装） |
| Node/pnpm 不污染用户环境 | 遵守（私有目录 + 子进程 PATH） |
| 不使用未验证版本组合 | 遵守（矩阵门禁，rc.8 被阻断） |
| 不引入 SnowLuma | 遵守（代码中零引用） |
| 不扩大插件库 | 遵守（仅 qqbot 1 个插件） |
| 不删用户配置/数据 | 遵守（卸载保留、回滚只删本次创建；已实测） |
| 不把 401 当作功能健康 | 遵守（三级健康） |
| 不以 Mock 代替真实 QQ 验收 | 遵守（门禁未通过） |

## 6. 下一阶段建议（M2 及并行事项）

**建议的顺序（按依赖）**

1. **补 Gate 0 缺口**：V02 已由 M1 覆盖；仍需 V08（范围评审）、V09（Desktop 真机）、V12（真人快测）。
2. **QQ-GATE-01 解锁**（最高优先，决定产品是否成立）：拿到凭据后执行 §4 的 6 项验收；通过前，UI 与文案继续显示"未通过"。
3. **M2 部署引擎收尾**：UI 取消/暂停、诊断包导出、Python/FFmpeg 适配（若产品确认需要）、组件事实表（`components.json`）。
4. **可重复性**：在 Win11 + 另一条网络复现 C1′；把集成测试接入 CI（`DDA_E2E=1` 的按需 job）。
5. **签名与分发**：按 B5 选 S0/S1/S2；S1 起需要 CI 预置签名凭据。
6. **许可**：就 `qqbot-connector` 向腾讯书面确认；在此之前 M4 离线项保持阻塞。

**不建议现在做**：Desktop 代下/代装、离线 QQ 包、个人 QQ 网关（许可与定位均未解锁）。
