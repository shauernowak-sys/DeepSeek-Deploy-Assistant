## 2. 官方能力盘点（这是 M3.1 复用的主体）

| # | 能力 | 来源（官方、可核查） | 结论 |
|---|---|---|---|
| A1 | 配置分层：bundle patch → profile `cordis.patch.yml` → home `cordis.patch.yml` → `--patch` | `dsh` README.zh「Profile」章节 + profile 文件内的注释 | **可用**：profile 自己的 patch 层就是官方允许用户改配置的地方 |
| A2 | patch 条目语义：顶层数组、按 `id` 定向覆盖，**同一 id 后写者生效** | 实验：同一 patch 内写两条 `agent-default-model`，`--dump-config` 显示后者生效 | **可用且可预测** |
| A3 | 组合结果自省：`--dump-config`（不启动进程） | `dsh --help` 列出该 flag；实测输出 1259 行组合树 | **可用**：天然的回读校验手段（CFG-2） |
| A4 | 配置 Schema 自省：`--dump-config-schema` | `dsh --help`；实测输出 841 KB JSON Schema | **可用**（该命令对个别无关插件 schema 报 warning 并 exit 1，但输出完整） |
| A5 | 凭据 seam：配置里只写 `apiKeyEnv`（引用名），值由 credentials 服务解析 | `dsh-credentials`、`dsh-credentials-local`、`dsh-llm-deepseek-api-key` README | **可用**：配置文件里**永远不需要出现密钥** |
| A6 | 凭据解析优先级：启动环境 > 存储文件 > 项目 `.env` > `$DSH_HOME/.env`；启动环境**只读且最高优先** | `dsh-credentials-local` README「密钥从哪里来」 | **可用**：让我们可以用「启动时注入环境变量」把密钥交给 Harness，不落盘 |
| A7 | 未配置/无效时给**具名错误**：`MISSING_CREDENTIAL`、`INVALID_CREDENTIAL`、`TRANSPORT` | 实测 `dsh headless` 输出 | **可用**：用于证明"密钥确实被 Harness 读到" |
| A8 | 模型路由：`agent-default-model.provider/model` 决定默认模型 | `--dump-config` 显示 `provider: deepseek-official, model: deepseek-flash` | **可用** |
| A9 | DeepSeek 官方路由 `deepseek-official`：Anthropic **Messages** 协议，默认 `https://api.deepseek.com/anthropic`，`/v1/messages` | `dsh-llm-deepseek` README「baseURL」表 | **可用**：连接测试必须按 Messages 协议探测 |
| A10 | 官方模型目录：`deepseek-flash`（文本+图片）、`deepseek-v4-pro`（文本），上下文 1,000,000 | `--dump-config-schema` 中 `models` 默认值 + README | **可用**：无需自己维护模型清单 |
| A11 | 自定义网关：`dsh-llm-pi-ai` 的 `providers.<route>`，`api` 取值 `openai-completions` / `openai-responses` / `anthropic-messages` | `--dump-config-schema`（`api` 的 enum）+ pi-ai README 示例 | **可用**：支持"兼容 OpenAI 的其它服务" |

## 3. 关键事实（本项目实现直接依赖）

| 项 | 实测值 | 验证方式 |
|---|---|---|
| Profile 路径 | `$DSH_HOME/profiles/<name>/cordis.patch.yml` | 文件本身存在，且首行注释写明"Your patch layer for this dsh profile" |
| 默认内容 | 注释 + `[]` | 实际文件 |
| 条目 id（web profile） | `llm-deepseek`、`llm-pi-ai`、`agent-default-model`、`credentials` | `--dump-config` 中逐一出现 |
| `llm-deepseek` 配置字段 | `apiKeyEnv`、`baseURL`、`models`、`reasoningEffort`、`thinking`、`maxTokens`、`defaultContextWindow` | `--dump-config-schema` |
| `llm-pi-ai` 路由字段 | `apiKeyEnv`、`displayName`、`api`、`baseURL`、`models[{id,name,contextWindow,maxTokens,…}]`、`compat` | 同上 |
| `agent-default-model` 字段 | `provider`（必填）、`model`（必填）、`reasoningEffort` | 同上 |
| 配置生效时机 | 写入 patch 后 `--dump-config` 立即反映；运行时由 HMR 热重载（未启用 HMR 时重启生效） | `dsh` README「Profile」 |
| 模型"存在性" | Harness **不探测远端**：目录是配置元数据，实际调用才可能失败 | `dsh-llm-deepseek-api-key` README「已知限制」 |

## 4. 被否决的方案（以及为什么）

| 方案 | 否决理由 |
|---|---|
| 把密钥写进 `$DSH_HOME/.credentials.yaml` | 虽然官方文档说该文件可编辑，但它是**明文 YAML**，直接违反 PRD §11 ③「明文不落盘」。改用启动环境注入（A6） |
| 调用 `dsh web` 的内部 HTTP/Typert API 写凭据 | 该 wire 协议未在公开文档中给出稳定契约（只有插件 README 描述 `ctx.remote.*` 语义），属于"猜测未公开接口"，违反 CFG-3 |
| 改 Harness 源码 / 改内部数据库 | 禁止项 |
| 自己实现模型客户端框架 | 禁止项；连接测试只做"一次最小请求 + 分类"，不是框架 |
| 让用户自己去终端敲命令 | 违反 §21 普通用户交互规范 |

## 7. 结论

M3.1 需要的每一项能力，Harness 0.2.0-rc.2 都已提供官方、可核查的机制：配置写在 profile patch 层、密钥走 credential seam、配置组合可自省。本产品因此**不需要**改 Harness、不需要自建模型框架，只需要：
1. 把用户填写的 provider/模型写成 patch 条目；
2. 把密钥保存在 DPAPI，并在启动 Harness 时作为环境变量注入；
3. 用 `--dump-config` 回读确认配置真的被 Harness 接受；
4. 用一次最小请求做真实连接测试与错误分类。
