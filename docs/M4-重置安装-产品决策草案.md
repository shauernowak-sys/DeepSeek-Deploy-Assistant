# 「重置安装」产品决策草案

**状态：** 草案，待产品决策（未开工，不阻塞 M4 收尾）
**日期：** 2026-11-05
**背景：** PRD §21.10 要求 4 个恢复动作：继续 / 重试这一步 / 回到上一可用 / 重置安装。前三个已可用（见 [M4-重试单步与视觉验收-实施报告](./M4-重试单步与视觉验收-实施报告.md)、[M4-恢复入口与安装E2E-实施报告](./M4-恢复入口与安装E2E-实施报告.md)），**"重置安装"至今没有定义**——这是本草案要解决的问题。

---

## 1. 为什么不能直接开写

现有三个动作的语义已经很清楚，但"重置安装"和它们的边界存在**真实歧义**，且三种理解都会动到用户数据：

| 动作（现状） | 做什么 | 不动什么 | 已可操作 |
|---|---|---|---|
| 继续（`task:resume`） | 从卡住的步骤继续跑到结束，已完成步骤不重跑 | 已完成的步骤、用户数据 | ✔ |
| 重试这一步（`task:retry-step`） | 只重跑当前卡住的那一步，成功后**停下** | 已完成的步骤、后续步骤 | ✔ |
| 回到上一可用（`task`→`profile:restore`） | 用备份还原 profile 的 4 个声明文件，并按 lockfile `--force` 重建依赖；**恢复前自动再备份一次** | 运行时（Node/pnpm）、Harness 本体、下载缓存、API 密钥 | ✔ |
| 回滚本次创建（`task:rollback`） | 删除**本次任务记录在案**的产物（Node/pnpm/Harness 目录、下载缓存），任务标记 `rolled-back` | profile、API 密钥、QQ 凭据、管理目录外的任何文件 | ✔ |
| **重置安装（未定义）** | ？ | ？ | ✘ |

三种最常见的用户诉求会落到同一个词上：

1. **"装坏了，从头装一遍"** → 期望清空运行时与 Harness，再装一次（= 回滚 + 重新部署）。
2. **"配置乱了，恢复干净状态"** → 期望清 profile/插件配置，保留已装好的运行时（= profile 重置）。
3. **"全清，当没装过"** → 期望连用户配置、下载缓存一起清（与 G-A2「不删除用户数据」直接冲突）。

**这三者是不同的产品决策，不是同一个按钮。** 先定义，再实现。

---

## 2. 候选方案

### 方案 A：不做（用组合动作替代）— **推荐**

- 界面上不新增"重置安装"，把"回滚本次创建…"的确认页文案补一句：**"回滚后可点『开始部署』重新安装（下载与包缓存会保留，通常更快）"**。
- 用户路径：回滚 → 开始部署。两步都是已验收的动作。
- 优点：零新增风险；不引入"一键删+装"的长事务；符合 N1/N5（不做通用软件管家）。
- 缺点：用户要理解两个按钮；"配置乱了"这类诉求仍没有一键入口（但可用"回到上一可用"覆盖大部分）。
- 成本：**0.5 人日**（仅文案 + 确认页说明 + 一条 FAQ）。

### 方案 B：语义化封装（重置 = 回滚 + 立即重装）

- 一个按钮完成：`rollback(confirmed)` → `start(fresh: true, planId)`。
- 必须回答：
  1. **权限**：重新部署仍需通过决策门禁（`planId` + `confirmed`），重置不能绕过——否则等于开了第二个执行入口；
  2. **失败面**：删完之后重装失败，用户会停在"什么都没装"的状态。是否允许？回滚只删我方产物，理论上可再装，但弱网下可能失败；
  3. **缓存**：保留下载缓存（快）还是清空（彻底）？两选项都要在确认页写清。
- 验收标准（若采纳）：① 二次确认页列出"将删除 N 个路径 / 将重新下载约 X MB / 预计 Y 分钟"；② 重装失败时保留回滚态并可直接重试；③ 不触碰 profile 之外的任何用户文件。
- 风险：**高**。这是"长事务 + 破坏性前置"，任何一步失败都要有清晰出路。
- 成本：3–5 人日（含 UI、失败路径、真实链路验证）。

### 方案 C：只重置配置态（保留运行时）

- 清 `dsh-home/profiles/web` 的声明文件与插件配置，保留 Node/pnpm/Harness。
- **直接冲突**：QQ 配置写在 `cordis.patch.yml`、插件配置在 profile 内 → 会被清掉，属于"删用户数据"。要落地必须先得到产品书面确认（等于给 G-A2 加一条豁免），并明确"重置前自动备份 + 可恢复"。
- 成本：2–3 人日 + 一次合规确认。

## 3. 推荐与理由

**推荐方案 A**，理由：

1. PRD §21.10 的四个动作里，前三个已经覆盖"坏了怎么办"的绝大多数场景；
2. 方案 B 的增量价值只有"少点一次按钮"：现状下"回滚 → 开始部署"已经能重装，而且 pnpm 包存储（`cache/pnpm-store`）本来就不在回滚范围内，无需重新下载大部分依赖（**注意**：`cache/downloads` 里的 Node 压缩包属于本次产物，回滚会删；详见 [决策材料 §0](./M4-重置安装-决策材料.md)）；
3. 方案 B/C 都涉及破坏性长事务或删用户配置，当前没有对应授权与验收标准，属于 M5 范畴。

**若产品仍要一键入口，请按方案 B1 立项**（删 → 重新检测 → 再确认 → 装），验收标准与失败路径见 [决策材料 §3](./M4-重置安装-决策材料.md)；**不要**用方案 C 的口径（它会删用户配置却容易被理解为"重装"）。

## 4. 需要产品书面确认的点

| # | 问题 | 建议默认 |
|---|---|---|
| Q1 | "重置安装"是否等于"回滚 + 重装"？ | 是（若要做，只能按方案 B） |
| Q2 | 是否允许通过"重置"清空 `profile`（含 QQ 与插件配置）？ | **不允许**（与 G-A2 冲突）；如允许需书面豁免 + 强制备份 |
| Q3 | 重装失败时的期望状态？ | 保持"已回滚、可重试"，不做自动多次重试 |
| Q4 | 下载缓存默认保留还是清空？ | 默认**保留**，确认页提供"同时清空缓存"复选项 |
| Q5 | 该入口放在部署页还是"故障诊断"页？ | 故障诊断页（语义上属于修复动作，不占部署主流程） |
