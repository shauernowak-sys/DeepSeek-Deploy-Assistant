### 1.5 V-M4-1 结论

1. **可以复用官方校验器**：`parseMarketIndex` 无运行时依赖纠缠（只需 `semver`），可独立于 `dsh` 版本使用；对 dsh `0.2.0-rc.2` 与本校验器 `0.2.1-alpha.4` **不存在版本兼容问题**（两者无耦合）。
2. **不能只依赖官方校验器**：PRD §10.2 的 **许可证、完整性哈希、验收方式、依赖闭包** 四项官方格式**完全没有承载位**，且多余字段被静默丢弃、不报错（用例 D）。→ **必须自建 overlay Schema**（zod），与官方格式分层存放。
3. **必填字段清单**（CI 必须校验）：根 `format`、`title`（含 `en`）、`plugins`；每个插件 `name`、`versions`（非空）；每个版本 `version`（精确 SemVer）、`publishTimestamp`、`source`。
4. **需要我方额外验证的字段**：`publishTimestamp` 是否与 registry 实际发布时间一致（校验器明确不检查）、`name/version` 是否与包实际一致、包是否声明了 `dsh.bundle`、图标尺寸/内容、`engines.dsh` 是否命中我方白名单组合。
5. **产品文案约束**：官方格式要求本地化文本**必须含 `en`**（`$.title must contain en`）。插件中心可以给中文，但索引里每条中文必须带英文回退，否则整份索引被拒。
6. **不支持的字段**：哈希、签名、许可证、依赖、验收方式、任意下载 URL、评分/评论（PRD 也已明确不做）。

### 3.2 关键发现：工具默认是禁用的

`dsh --profile web --dump-default-config` 中 `tool-plugin-manager` 出现 4 次：

### 4.3 Registry 回退机制（D06 的关键约束）

`dsh-plugin-manager` 自带 registry 计划与失败归因（`lib/types/registry.js`），实测结果：

| 配置 | 实际询问顺序 |
|---|---|
| `configured.registry=official`，`fallbacks=[]`，pnpm 自身=official | `[npmjs]` |
| `configured.registry=official`，`fallbacks=[npmmirror]`，pnpm 自身=official | `[npmjs, npmmirror]` |
| `configured.registry=npmmirror`，`fallbacks=[npmjs]`，pnpm 自身=**npmmirror** | **`[npmmirror]`（回退被关闭）** |
| 请求私有源，但不在配置集合中 | `[私有源]`（**不落到公共源**，安全设计） |

源码规则（`registryPlan`）：**只要 pnpm 自身的 registry 既不是官方 npm，也不在 fallback 列表里，就"单独询问"，不再回退。**

**判定：** 现象可复现（多次运行均出现），最可能的原因是 **pnpm 复用了本机既有的 npmjs 元数据缓存**（本机此前多次用官方源安装过同一批包）。本次尝试用 `--store-dir` / `--cache-dir` / `npm_config_cache_dir` 隔离缓存，**未能可靠改变该行为**，因此：

- **结论定性为"高置信度现象 + 中等置信度成因"**：不能断言镜像一定会被全部使用。
- **对 D06 的要求**：① 必须在**干净机器/干净 pnpm 缓存**上复测本项；② 产品需记录**每个 tarball 的实际 host**（pnpm 的慢速告警已证明该信息可得）；③ 不得仅凭"registry 配置为镜像"就对用户承诺"全部走国内下载"。

#### 4.5.4 端到端：直连安装 + 加载

在直连环境下用 npmmirror 安装后启动 Host（隔离 `DSH_HOME`、独立端口 47931）：

- stdout 出现插件的中文引导与**真实绑定入口**（`https://q.qq.com/qqbot/openclaw/connect.html?task_id=558feff9…&source=dsh-qqbot`）→ **插件已加载**；
- `boot-direct.err` 大小 0 字节 → **无加载错误**；
- 强杀进程后 `Get-NetTCPConnection -LocalPort 47931 -State Listen` 为空 → **端口随进程释放**。

### 4.6 V-M4-4 结论

1. **已证明"无 VPN 直连可安装核心插件"**：在真实国内网络（单默认路由、无 TUN、真实 DNS）下，官方源与 npmmirror **均 37/37 安装成功**，且两源 tarball 字节完全一致、integrity 与官方声明相符。
2. **镜像显著更快**：插件主包 624 vs 33 KiB/s（约 19 倍），元数据 46 ms vs 884 ms。→ **D06 的"镜像优先"策略有实测依据。**
3. **但"配置镜像"不等于"全部走镜像"**：多次观察到部分 tarball 仍从 `registry.npmjs.org` 下载（1–43 KiB/s），怀疑是 pnpm 跨源元数据缓存复用。→ **D06 必须记录实际 host，并在干净机器复测。**
4. **遗留代理环境变量会严重拖慢安装**：`HTTP_PROXY` 指向已关闭端口时，`npm view` 从 <1 s 退化到 **70.6 s**。产品把 `process.env` 原样传给 dsh 子进程（`dshEnv()`），因此**必须检测并处置失效代理**（`Q-PROXY-ENV`）。
5. 代理环境下的旧数据（3.6 s / 6.0 s pnpm）**作废**，不再作为结论依据。
6. Gate 4 ① 由"未通过（证据不足）"改为 **通过（附两条限制：tarball host 需复核、失效代理需处置）**。

## 7. V-M4-7：插件篡改与哈希校验验证

### 7.1 现有能力（M2 安装编排）

`packages/core/src/transfer/downloader.ts`：

- `downloadVerified()`：多源顺序尝试、每源重试、HTTP Range 续传、**强制 SHA-256**、`.part` 原子改名、大小复核；
- `verifyHash()`：定长比较（位异或累加），长度不同直接 false；
- 哈希不一致 → `rm(partPath)` 删除临时文件 → `break` 跳出该源重试 → 换下一个源；
- 全部源失败 → 抛 `DdaError`。

### 7.2 实测（真实插件包，不是构造数据）

测试使用**真实** `@tencent-connect/dsh-qqbot@0.5.5` tarball（225 458 B） + 本机 HTTP 服务，调用产品自身的 `downloadVerified`（临时测试文件 `tests/core/__m4-temp-tamper.test.ts`，**跑完即删除**；`git status` 已确认无残留）。

| 步骤 | 结果 |
|---|---|
| 原始 SHA-256 | `f9442c91e29d1dca…` |
| 翻转中间 1 字节后的 SHA-256 | `d74e41ffe2c0836a…`（与原始不同） |
| 原包 + 正确哈希 | **通过**，落盘大小 225 458 B，返回的 `sha256` 与清单一致 |
| 篡改包 + 原始哈希 | **被拒绝**；`bad.tgz` 与 `bad.tgz.part` **都不存在**（临时文件已清理） |
| 篡改包 + 篡改后的哈希 | **通过**（正常行为，说明"清单哈希是唯一防线"） |

### 7.3 发现的缺陷（本次不修，记录为 M4 前置修复项）

1. **错误码不可读**：篡改被拒后对外抛出的 `DdaError.code` 是 **`E_DOWNLOAD_NETWORK`**，不是 `E_HASH_MISMATCH`；`action` 字段为空字符串。用户看到的是"检查网络连接与镜像可用性"，而不是"内容与清单哈希不一致，可能被篡改"。
   证据：`downloader.ts:150-158`（内层 `break` 后仍走外层聚合），以及现有测试 `tests/core/downloader.test.ts:87` —— **测试标题写"抛 E_HASH_MISMATCH"，断言却是 `E_DOWNLOAD_NETWORK`**。
2. **`packages/core/src/diagnose/rules.ts:13`** 用 `/sha256 mismatch/i` 匹配消息文本兜底，说明团队已知此行为，但门禁口径未统一。
3. **插件安装路径没有 SHA-256 校验**：插件安装走 pnpm 的 lockfile integrity（sha512），我方清单哈希**未参与**。若插件中心要承诺"清单哈希校验"，D03 必须补上"下载→校验→`file:` 安装"路径（D04 的本地导入即可承接）。

### 7.4 V-M4-7 结论

- **篡改包会被拒绝**：✅ 成立（文件不落盘、不安装、临时文件清理）。
- **不存在绕过哈希校验的备用安装路径**：⚠️ 对**我方下载器**成立；对**插件安装**不成立（pnpm 用自己的 integrity，我方清单哈希不参与）。
- **不会删除用户已有文件**：✅（只删 `<dest>` 与 `<dest>.part`，`dest` 由调用方给定）。
- **错误提示不够明确**：❌ 需修复（错误码与 action 文案）。

1. **安装执行方不是 Agent，而是"用户明确动作"**：主路径用 `dsh plugin --profile web add <精确 spec>`（实测可用、可日志、可回滚）；Agent 路径列为"未验证能力"，不得作为唯一路径或对外承诺。
2. **索引与安装解耦**：索引（官方 format 1 + 我方 overlay）只用于**展示与校验**；安装规格由我方 `marketInstallTarget()` 等价位逻辑产出，不依赖 Harness 读取索引。
3. **D10 顺延**：本地索引托管在锁定版本不可能；等宿主升级并启用 experimental market bundle 后再评估，且届时仍需重做 QQ 兼容验收。

**不推荐现在切方案 A 的理由：** 需要先把 Harness 升到 `0.2.1-rc.x`（`compat.json` 现为 `unverified`，禁止安装）→ 必须重做 M0 级别的启动/插件/QQ 验收 → 且 market 仍是 experimental 可选 bundle。这是"用一个未验证的宿主版本换一个 experimental 功能"，与本项目"只卖经过验证的组合"的定位冲突。
