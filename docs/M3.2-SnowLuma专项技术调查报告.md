## 4. 第三步：SnowLuma 与 Harness `0.2.0-rc.2` 的兼容性

### 4.1 架构分层（为什么"兼容性"不是直接耦合）

```
QQ NT (QQ.exe) ←hook→ SnowLuma 运行时 ──OneBot v11 HTTP──→ dsh-qq-link ──ctx.agents──→ Harness 0.2.0-rc.2 ──→ DeepSeek API
```

| 边界 | 协议 | 版本耦合点 | 兼容性判定 |
|---|---|---|---|
| QQ ↔ SnowLuma | 官方 NTQQ 进程 hook | **QQ 版本**（非 Harness） | SnowLuma 自带兼容清单，`allowUnknown=true`；**待真实环境验证** |
| SnowLuma ↔ 适配插件 | OneBot v11 HTTP（`127.0.0.1:3000`） | 无版本耦合（HTTP 契约） | ✅ 默认端口/路径天然一致 |
| 适配插件 ↔ Harness | Cordis 插件 + `ctx.agents` | **Harness 版本** | ✅ **B-X1 已实测**：`dsh-qq-link@1.5.1` 在 `0.2.0-rc.2` 上可加载（§5） |

**结论：SnowLuma 本身与 Harness 版本无关**；真正需要版本匹配的只有适配插件，而它已经是实测可用的。这也意味着**不需要升级 Harness 基线**。

### 4.2 端点/参数对齐明细

| 项 | SnowLuma 默认 | `dsh-qq-link` 默认 | 是否对齐 |
|---|---|---|---|
| 基地址 | `http://127.0.0.1:3000` | `NapCat: http://127.0.0.1:3000`（字段名叫 NapCat，实质是 OneBot base URL） | ✅ 完全一致 |
| 鉴权 | `accessToken` **随机生成**（存于 `config/onebot*.json`） | 配置项"令牌" | ⚠ 必须由我们**读取并填入**，否则请求被拒 |
| 消息格式 | `messageFormat: "array"` | 插件按 array 解析 | ✅ |
| 轮询 | SnowLuma 提供 `get_friend_msg_history` / `get_group_msg_history`（OneBot 标准） | 插件 README 列出的正是这两个 | ✅ |
| 发送 | `send_private_msg` / `send_group_msg` | 同 | ✅ |

### 4.3 尚未验证的兼容性风险

| 风险 | 说明 | 何时能验 |
|---|---|---|
| QQ 版本 hook 不匹配 | native hook 与 QQ 版本对不上 → 注入失败 | 需真实 QQ 登录（用户操作） |
| 插件对 SnowLuma 的"未经声明"假设 | `dsh-qq-link` README 称 SnowLuma 为其**主力测试后端**，但版本未钉死 | 真实验收时记录版本对 |
| Harness 侧 `ctx.agents` 行为差异 | 插件声明 `0.2.1-rc.3` 兼容，我们在 `0.2.0-rc.2` 使用 | 已加载成功；边界功能（面板/语音）不纳入依赖 |

## 6. 第五步：自动安装 / 配置 / 启动 / 授权 / 检测 流程设计

> 设计原则：**形态 A 与形态 B 共用同一状态机与检测器**，只在"谁来执行安装/启动"这一层分叉。这样无论授权是否到位，工程量不会翻倍。

### 6.1 形态 A（**已获书面授权**）：全自动

```
① 前置检查   QQ NT 已安装？QQ 是否在运行？端口 3000/3001/5099 是否被占用？
             ↓ 缺 QQ → 引导安装（腾讯官网入口，不代装）
② 下载       按 manifest 固定版本 v2.4.0 从官方 Releases 下载（L3）；
             失败→公共代理前缀（ghfast/gh-proxy，透传，不入我方资源库）；SHA-256 强制校验
③ 解压安装   解压到 %LOCALAPPDATA%\DeepSeekDeployAssistant\components\snowluma\2.4.0\（我们自己的目录）
             记录 install.json（版本/哈希/时间/来源 URL）
④ 首次运行   以"与 QQ 相同用户"启动 node.exe index.mjs（cwd=安装目录）
             环境：SNOWLUMA_ONEBOT_HTTP_PORT=3000、SNOWLUMA_WEBUI_PORT=5099、
                   SNOWLUMA_UPDATE_CHECK=0（钉版本）；
                   EULA/PRIVACY 由用户在界面上勾选后才设置 ACCEPT 变量
⑤ 授权引导   展示 WebUI 地址 + 从启动日志捕获的一次性初始密码
             → 让用户在 QQ 窗口里扫码登录（**只能用户做**）
             → 提示在 WebUI 里确认 hook 已加载
⑥ 打通       读 SnowLuma 的 config/onebot*.json 取 accessToken（只读、不落日志）
             → 安装/校验 dsh-qq-link@1.5.1 → 通过其 /save 路由写入 OneBot 地址与令牌
⑦ 检测       六段式状态机（§6.3），"联通"必须来自实时证据
⑧ 收尾       提示"发一条消息试试"；失败给可执行下一步
```

### 6.2 形态 B（**未获授权** —— 默认兜底）

```
① 说明     一屏说清：为什么必须由你手动装（许可证原文 + 链接），我们做什么、不做什么
② 官方入口 可点击/可复制的 Releases 链接（钉到 v2.4.0 的页面）+ 安装步骤卡片（含截图位）
③ 自检      用户装好后点"我已安装，开始检测" → 检测安装目录/版本/进程/端口
④ 启动引导  告诉用户双击 launcher.bat（或"我帮你启动"**仅限用户已在本机安装**时提供，且需授权口径确认）
⑤ 授权引导  展示 WebUI 地址 + 让用户从控制台复制初始密码 → 扫码登录
⑥ 参数复制  把 OneBot 地址/令牌以"复制"按钮交给用户，用户在 WebUI / dsh-qq-link 设置页粘贴
⑦ 检测      同一套六段式状态机
```

### 6.3 运行检测：六段式状态机（两形态共用）

| 段 | 判定依据（必须有证据行） | 失败时给用户的下一步 |
|---|---|---|
| `qq-missing` | 注册表/常见路径找不到 `QQ.exe` | 给腾讯官网下载入口 |
| `qq-not-running` | 进程表无 `QQ.exe` | "请先打开 QQ 并登录" |
| `snowluma-not-installed` | 安装目录/`release.json` 不存在 | 按形态给下载或手动步骤 |
| `snowluma-installed` | 目录 + `release.json` 版本可读（校验与 manifest 一致） | "下一步：启动 SnowLuma" |
| `snowluma-running` | 进程存在（真实进程名，需实测确认）**且** `5099` 可连 | "打开 WebUI 完成登录" |
| `onebot-reachable` | `POST/GET` OneBot `get_login_info`（带 token）返回 200 且含 QQ 号 | "在 WebUI 里检查 OneBot 服务与令牌" |
| `harness-linked` | `dsh-qq-link` 的 `/dsh-qq-bridge/state` → `ok:true`，且其 `NapCat状态` 无 `错` | "点『重新检测』；检查两端端口/令牌是否一致" |
| `message-verified` | 真实一轮 QQ 往返（见 §7） | —— |

**禁止**：进程在就显示"已连接"；端口通就显示"已联通"；配置存在就显示"可用"（PRD §10.4 五段证据原则）。

### 6.4 数据边界（不碰用户的东西）

| 对象 | 我们的行为 |
|---|---|
| SnowLuma 安装目录（形态 A 下是我们创建的） | 只解压、不改文件；卸载时只删我们自己创建的那份 + `install.json` 记录 |
| SnowLuma 安装目录（用户自己装的，形态 B） | **只读检测**；不删除、不修改 |
| `config/onebot*.json`（含 accessToken） | 只读取 token 用于本地联调；**不写日志、不进诊断包、不上传**；UI 只显示掩码 |
| QQ 目录 / QQ 登录态 | 完全不碰 |
| 我们的 state | `state/personal-qq.json`（选择的组件、端口偏好、上次检测结果） |

## 7. 第六步：个人 QQ 真实消息收发验收标准（QQ-GATE-02 · SnowLuma 版）

> 口径：**Mock 与真实分开统计**；每项都要有"环境 / 步骤 / 真实结果 / 脱敏证据 / 通过与否"五要素；**不支持就写不支持**。

| # | 验收项 | 判定标准（必须可复核） | 前置 |

| 1 | 组件就位 | SnowLuma 版本 = `v2.4.0`（或 manifest 指定版本），文件哈希与 manifest 一致；`release.json` 可读 | 形态 A 自动 / 形态 B 手动 |

| 4 | 适配层联通 | `dsh-qq-bridge/state` → `ok:true` 且 `NapCat状态` 无错；配置里的端点/令牌与实际一致 | 3 + 插件已装 |
| 5 | **私聊 → Harness** | 用**另一个 QQ** 私聊目标号 → Harness 侧出现新会话/新轮次（会话文件或日志为证） | 4 + API 已配置 |
| 6 | **Harness 调用 DeepSeek** | 同一轮的模型调用成功（M3.1 已验证的链路日志/`verdict=ok`） | 5 |
| 7 | **回复回到 QQ** | 对端 QQ 实际收到 AI 回复（人工确认 + 截图） | 6 |
| 8 | **群聊 @** | 测试群内 @机器人 → 群里收到回复（若 SnowLuma/插件默认策略不响应，需在插件侧开启并记录配置） | 4 |
| 9 | 图片消息 | 私聊发一张图片 → Harness 侧收到（`media` 开关开）；"看懂"不做承诺 | 4 |
| 10 | 断线恢复 | 断开网络 30s → 恢复 → 不重启任何进程，再发一条能收到回复 | 7 |
| 11 | 重启恢复 | 关闭助手 → 重开 → 启动 Harness 与（形态 A）SnowLuma → **QQ 无需重新扫码**（SnowLuma 登录态仍在）→ 再发一条能收到 | 7 |

- 任何一项**不得**用 Mock、回环、截图伪造替代（对齐 PRD QG-3）。
