## 1. 一页结论

> **DeepSeek Deploy Assistant 目前不是"接近完成的 V0.1"，而是"核心部署与两条 QQ 路线的代码骨架已完成、但 V0.1 冻结需求中仍有 97 项未达标（其中 P0 9 项）的半成品"。**
>
> 亮点很实在：**Harness 安装链路（13 步、幂等、可恢复）**、**API 配置（DPAPI + 真实连接测试 + 写配置回读 + 回滚）**、**个人 QQ 检测/引导/适配层**、**诊断包与脱敏**、**数据保护与回滚边界** 都是"有代码 + 有测试 + 有实机证据"的真交付。
>
> 但**冻结 PRD 的 V0.1 P0 能力里，插件资源中心（索引/详情/离线/国内三层/五段证据/许可字段）完全没有开始**，而它在 PRD 里被列为 V0.1 必须（§10、§20.2、A7/A8/A9）。同时**界面仍是"M2 原型"单页控制台**，没按 §21 交付首页/确认页/完成页；**路线检测不构成任何门禁**（已装 Desktop 或信号矛盾时仍可一键安装）。

| 维度 | 结论 |
|---|---|
| 代码质量基线 | **良好**：TS strict 0 错误、279 单测通过、分层清晰（spec/core/adapters/app）、无 shell 执行、zip-slip 防护、日志脱敏有单测 |

## 3. 最严重的五个产品缺口

### 缺口 1（P0）｜插件资源中心整体缺失，而它是 V0.1 的 P0 需求

**证据：** 仓库无 market/index 模块，`package.json` 未引入 `@deepseek-ai/dsh-plugin-market-index`，无 `index.json`、无插件详情、无分类/搜索、无离线导入、无 L1 资源库（U5 未决）、无五段证据徽标（`PLG-1/2/4/5`、`CN-4/7`、`A7/A8/A9` 全部未达标/部分）。

**为什么严重：** PRD §20.2 把"§10 资源库（核心清单 + 元信息字段 + 哈希校验 + 三层下载 + 许可判定）"列为 V0.1 **最低实现**；§4.1 把 PLG-1..PLG-5 全列为 P0。当前用户能装的插件只有**硬编码的一个**官方 QQ 插件，产品定位里的"清单驱动的部署编排器"只实现了半句。

**影响：** V0.1 无法达成 G4（"提供经过验证的插件资源"）；A7/A9 直接不成立。

---

### 缺口 2（P1）｜安装动作无确认、路线判定不设门禁——用户可能在"已有 Harness"的机器上盲目重装

**证据：**
- `App.tsx` 的"开始部署"直接调用 `api.startDeploy()`，**没有任何确认对话框**（对比：取消部署/删除 API/导出诊断都有确认）。PRD §5.2 R1、§21.4 明确要求"装什么/装到哪/占多大/要多久"。
- `detectRoute()` 能返回 `multiple` / `unknown`，但 `DeployService.start()` 完全不检查 route；UI 只把一个 badge 变红，按钮照旧可点。PRD §6.2 要求"并存时强制选择""矛盾时禁止猜测后安装"。
- `isWritableProfile()`（`packages/core/src/detect/route.ts:72`）是死代码；`pathDshVersion` 只来自环境变量 `DDA_ASSUME_PATH_DSH`（`env-service.ts:50`），**并不真的探测 PATH 上的 dsh**。

**影响：** 一个已经装过官方 Desktop 的普通用户，会在没有任何提示的情况下被装上第二套 Harness，且不知道两套 profile 互不通用——这正是 PRD 风险清单第 10 条要防的场景。

---

### 缺口 3（P1）｜"五态检测 + 系统 Node 复用"没有实现，A2 验收项不成立

**证据：** `RuntimeInfo` 只有 `installed/version/path`（`packages/spec/src/domain.ts:24`）；`env-service.ts:18` 只调用 `detectManagedNode`；`manifest.detect.minVersion/acceptExisting` 从未被读取；`D-1/D-6` 未实现、`D-5` 部分。

**影响：** PRD §7.2 整整一张"复用与私有运行时策略"表（含"有多个 Node（nvm）默认不复用""用户主动选择隔离模式"）没有对应实现；A2 的"含已有 Node 的复用判定"无法验收。用户机器上已有 Node 22 时，软件仍会再下 35 MB 装一份私有运行时——不致命，但与"不污染、可解释"的产品承诺不符。

---

### 缺口 4（P1）｜界面仍是"M2 原型"单页控制台，§21 的六条交互原则大部分未落地

**证据：** `App.tsx` 页头自述"**M2 原型 · 0.2.0**"；单页 6 个区块全展开（环境/运行状态/部署/QQ/门禁诊断/API）+ 个人 QQ 五步向导嵌在页签里。逐项对照：§21.2 首页 ❌、§21.4 安装确认页 ❌、§21.11 完成页 ❌、§21.10"重试这一步/回到上一可用/重置安装" ❌、§21.8 资源库 ❌、UX-2"一屏一件事" ❌。

**影响：** 目标用户是"P1 非技术尝鲜者"。当前界面同时出现 `dsh 0.2.0-rc.2`、`pnpm`、`profile`、`OpenID`、`cordis.patch.yml`、`AppID/AppSecret`，且"下一步"有 5 个并列主按钮。A14（3 名零基础用户独立完成）在这种情况下几乎不可能通过。

---

### 缺口 5（P1）｜交付能力缺手册、向导、签名与第三方声明；对外文档已与事实脱节

**证据：**
- 无使用手册、无故障排查文档、无首次启动向导（`docs/` 全部是研发文档；根 README 仍写"已实现能力（M2）""174 通过"，实际 279）。
- 无 `THIRD_PARTY_NOTICES.md`、无 `licenses/` 目录；`node.json` 引用的 `licenses/node-LICENSE.txt` **文件不存在**；`AppPaths.licenses` 零写入。
- 未签名（S0），安装包元数据 `Copyright 漏 2026`（乱码）。
- `compat.json` 的 evidence 含本机绝对路径 `C:\dda-m0-lab\logs\...`，仓库外无法复核。

**影响：** 即使功能补齐，也无法作为"正式交付"发布（G-C 常规门禁 + G-B3 签名决策 + 用户文档）。同时对外口径（README/PRD 状态列）已经落后于实现，容易被误读为"已完成"或"未完成"，两头都不利。

## 8. 总体结论

1. **已交付的部分是扎实的**：Harness 安装链路、API 配置、个人 QQ 检测与适配、诊断与脱敏、数据保护边界，都做到了"代码 + 单测 + 实机证据"三件套，且 M2.1 的独立复核确实修掉了 P0 级数据删除缺陷。这是可以继续往前走的底子。
2. **V0.1 尚未达成**，且缺口不是"打磨"，而是**整块能力缺失**：插件资源中心（P0）、§21 交互（P1）、环境检测五态与复用（P1）、安装决策门禁（P1）。
3. **两条 QQ 路线的代码侧已到位，真实链路仍由用户验收决定**：QQ-GATE-01 保持 **2/6**、QQ-GATE-02 保持 **0/12**。本次审计未提升任何门禁计数，也不应提升。
4. **不存在"技术不可行"的阻塞**：所有未实现项都有明确实现路径，唯一真正的外部阻塞是 **U5（L1 资源库）**、**U18（SnowLuma 授权）**、**U3（Desktop 安装包）** 与 **U14（远程清单）** 四项产品/许可决策。
5. **建议不要再往 M4 之后规划**：M4（插件资源中心）本身就是 V0.1 的 P0 需求，应视为"V0.1 最后一块拼图"，而不是下一代功能。

**因此，下一步不是"开始 M4"，而是先完成 M3 收口 + 一个明确的 V0.1 收尾清单（见[后续开发路线建议](./V0.1-后续开发路线建议.md)），再按前置条件启动 M4。**
