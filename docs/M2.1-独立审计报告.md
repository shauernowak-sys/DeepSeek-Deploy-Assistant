## 3. 诊断报告安全性（重点审计项 1）

### 3.1 审计方式

不看"正则漂不漂亮"，而是分三层验证：

1. **结构化边界**：报告里到底放了什么（是否只放白名单字段、是否可能带入 profile 文件内容）；
2. **脱敏函数的对抗测试**：用"修正前"的真实缺陷样本逐条断言；
3. **端到端字节扫描**：打包应用真导出 ZIP → 解压 → 逐段扫描用户名/密钥/密钥字段。

### 3.2 发现并修复的缺陷（详见 [修复记录 D1–D4](./M2.1-修复记录.md)）

| 编号 | 缺陷 | 严重度 | 影响 |
|---|---|---|---|
| D1 | `sanitize(text, '')` 会用 `replaceAll('', '<user>')` 把占位符插进**每两个字符之间** | **P0** | 一旦 `USERPROFILE` 为空（服务/特殊会话/精简环境），诊断报告变成乱码；且**用户目录完全失去脱敏**（正文已被摧毁，无法再替换路径） |
| D2 | 旧的 `\b\d{9,}\b` 只覆盖 9 位以上数字；QQ 号 5–8 位完整保留；`app_id` 写法不匹配旧 `appId|appid|AppID` 规则 | **P1** | QQ 号（个人标识）可能进入诊断包 |
| D3 | 旧规则只认 3 种形状（`sk-`、`appSecret`、`QQBOT_SECRET`）；`DEEPSEEK_API_KEY=`、`api_key:`、`apiKey=`、`token=`、`password=`、`Authorization: Bearer …`、`openid=` 均**原样输出** | **P0** | 日志一旦出现这些行，凭据直接进 ZIP |
| D4 | `preview()` 与 `export()` **各自重新采集一次** | **P1** | 预览后日志继续增长/网络探测结果变化 → 用户看到的和 ZIP 里的不是同一份内容，预览失去"知情同意"意义 |

### 3.3 修复后的实际行为（本轮实测）

- 打包应用（0.2.0 最终包）真导出：预览 7 段字节数 `179/146/87/2/31/351/208`，解压 ZIP 后逐项**完全一致**（见 [m21-packaged-ui-diagnostics.log](./evidence/m21-packaged-ui-diagnostics.log)）→ 预览 = ZIP。
- 同样 7 段全文扫描：`用户名=False`、`sk-=False`、`密钥字段=False`（逐段一行记录在证据里）。
- `01-system.txt` 实测：`数据目录: <user>\AppData\Local\DeepSeekDeployAssistant`（用户目录已替换）。

### 3.4 QQ ID 与用户目录处理

| 场景 | 处理 |
|---|---|
| 用户主目录（`C:\Users\<name>`） | 反斜杠 / 正斜杠 / 末尾斜杠 / JSON 二次转义 4 种写法统一替换为 `<user>` |
| 用户名单独出现 | 长度 ≥3 时替换为 `<user>` |
| QQ 号 / `uin` / `user_id` / `group_id` / `guild_id` / `channel_id` / `openid` / `unionid` | 名称+值整体脱敏（`qq=[redacted]`），**含 5–8 位**；无名字前缀的 9 位以上数字串 → `<digits>` |
| QQ 机器人 `appId` / `app_id` | `appId=[redacted]` |

### 3.5 诊断包是否可能包含 Profile 敏感文件**内容**？

**不会。** `03-profile.txt` 只做 `readdir` 递归列目录（深度 2，最多 200 条，只输出相对路径），从不 `readFile`。本轮用"profile 内放置含 `apiKey` 的 `config.json`"反向测试：段内只有 `config.json` 文件名，没有 `apiKey`，也没有密钥值。日志段只读 `logs/*.log`（最多 3 个、各取末 32 KB），且**写日志时已脱敏一次、进诊断包时再脱敏一次**。

### 3.6 残余风险（必须写进发布说明，不得隐匿）

1. 脱敏是**模式驱动**的：一个既不叫 `*key/token/secret/password*`、也不是 `sk-`/`Bearer`/长数字形状的凭据值，仍可能漏过。缓解措施是结构性的（不打包 profile 内容 + 日志写入即脱敏 + 预览可取消），而非"正则已穷尽"。
2. `sanitize()` 依赖 `USERPROFILE`：若为空（D1 场景），路径脱敏会**整体跳过**（这是刻意的安全取舍——宁可少替换，也不摧毁报告）。此情形下诊断包可能包含完整路径，UI 预览是用户唯一的拦截点。
3. 长十六进制哈希（如 sha256 校验值）**故意不脱敏**，因为它们不是凭据且是排障关键信息。

**本轮修复的残留空目录（K-M2-11）**：修复前静默卸载后 `%LOCALAPPDATA%\Programs\DeepSeek Deploy Assistant` 会剩下一个**空目录**。根因是卸载器以该目录为工作目录（Windows 持有句柄），`RMDir` 失败。修复见 [D8](./M2.1-修复记录.md)（NSIS `customUnInstall`：先切走工作目录重试一次，仍失败则用 `rmdir`（无 `/s`）延迟回收——**只能删空目录**，用户放进安装目录的文件绝不会被删）。

**用户数据边界（实测）**：卸载后 `%LOCALAPPDATA%\DeepSeekDeployAssistant` 与预置 `sentinel.txt` 完好；`deleteAppDataOnUninstall: false`，安装器**没有**任何"删除用户数据"的默认动作。

**"完全清理必须经过用户确认"**：产品内唯一会删除用户可见文件的入口是"取消…→ 同时清理本次任务创建的文件"勾选框，弹窗会列出 `created[]` 中的路径与"当前存在 N 个"，用户可取消整个动作；`diag:export` 必须带 `confirmed:true` 才落盘。**卸载器的"清理"仅限程序目录，不涉及用户数据，因此不需要额外确认**。

## 5. 版本信息（重点审计项 3）

### 5.1 `FileVersion = 33.4.11` 的根因（已定位）

不是"版本号写错"，而是**版本资源根本没被写进去**：

1. 旧配置 `win.signAndEditExecutable: false`（M1 引入，为了绕开 `winCodeSign` 下载）**同时关闭了 rcedit**，于是 exe 保留 Electron 自带资源 —— Electron 33.4.11 的 `FileVersion` 就是 `33.4.11`。
2. 本轮尝试打开该开关后**构建直接失败**：electron-builder 25.1.8 在 Windows 上走 `app-builder rcedit`，而该命令仍会先解析 `winCodeSign` 工具链；`winCodeSign-2.6.0.7z` 内含 macOS 符号链接，**非管理员账户无法创建**，7z 解压失败 → 构建中断（这就是旧注释里"需要符号链接权限"的真实来源）。
3. 结论：**"版本资源"与"签名工具链"在 electron-builder 里被绑死**，在非管理员机器上不可两者兼得。

### 5.2 修复（详见 [D7](./M2.1-修复记录.md)）

改为两段式构建：`electron-builder --dir`（不碰签名）→ `scripts/set-win-version.mjs`（用纯 JS 的 `resedit` 直接改 PE 版本资源）→ `electron-builder --prepackaged release/win-unpacked` 出 NSIS。**零管理员、零外部下载、可 CI 复现**。

### 5.3 最终一致性（实测值）

| 位置 | 值 | 证据 |
|---|---|---|
| `package.json.version` | `0.2.0` | 源文件 |
| `app.getVersion()` / 界面页头 | `0.2.0`（"M2 原型 · 0.2.0"） | m21-packaged-ui-diagnostics.log |
| 程序 exe `FileVersion` | `0.2.0` | 安装后 `Get-Item .VersionInfo` |
| 程序 exe `ProductVersion` | `0.2.0.0`（Windows 四点式，等价 0.2.0） | 同上 |
| 安装包 `FileVersion` / `ProductVersion` | `0.2.0` / `0.2.0` | 同上 |
| 安装包文件名 | `deepseek-deploy-assistant-0.2.0-x64.exe` | 构建产物 |
| 注册表 `DisplayVersion` | `0.2.0` | 安装实测 |

仍为空的两项（不阻塞，记入已知问题）：注册表 `Publisher` 与 `InstallLocation`（electron-builder 未写；`Publisher` 为空源于 `package.json` 没有 `author` 字段）。

## 6. Windows 兼容性（重点审计项 4）

### 6.1 M2 的 Win10 结论有多硬？

- **审计结论：M2 的"Win10 通过"只能算"构建环境证据"，测试侧的 OS 归属无法从留档重建。** 这是证据链缺陷，不是功能缺陷，本轮已在新报告中改用可核查的写法。

### 6.2 本轮的真 Win11 结果（新增证据）

本轮全部工作（typecheck / 90 用例 / 真实部署 / 打包 / 四种安装卸载 / CDP 诊断导出）都在 **Windows 11 Pro 10.0.26200、非管理员**上完成，且操作系统版本同时由 `Win32_OperatingSystem` 与诊断包 `01-system.txt`（`操作系统: Windows_NT 10.0.26200`）双向印证。

因此 **"支持 Win11"从"未验证"提升为"真机通过（非干净机）"**。

### 6.3 为什么仍然不能算"第二环境验收通过"

| PRD 第二环境条件 | 本轮状态 |
|---|---|
| Windows 11 | ✅ 是 |
| 无 Node / pnpm / Harness | ❌ **不满足**（系统自带 Node 24.21.0；本轮为构建安装了 pnpm） |
| 非管理员 | ✅ 满足 |
| 国内网络 | 部分（镜像与官方源均可达） |
| 10 项场景全跑 | 部分（部署/诊断/安装卸载已跑；QQ 无凭据） |

**结论：Win11 第二环境 = 部分验证（操作系统层面通过，干净机前提未满足），不得标记为通过。**

### 6.4 Win11 第二环境验收方案（可执行清单）

1. 准备 Win11 24H2/25H2 干净机（或 Hyper-V/VMware 快照），**不装 Node/pnpm/dsh**，使用普通用户账户。
2. 记录 `winver` 与 `[Environment]::OSVersion`，并截图。
3. 拷贝 `deepseek-deploy-assistant-0.2.0-x64.exe`（先校验 SHA-256 = `08070338367AD04856A739E7D45023E52598C199D35D2928A5DC829C1B2306F6`）。
4. 静默安装 → 启动 → 环境检测 → 完整部署（13 步）→ 导出诊断 → 卸载；每步留日志。
5. 断网/弱网各跑一次下载步骤，确认镜像回退与错误分类文案。
6. 若同时有 QQ 凭据，追加 QQ-GATE-01 五项（扫码/收发/图片/重连/重启恢复）。

## 7. 审计中额外发现的缺陷（不在原定 5 个重点内，但属真实缺陷）

| 编号 | 缺陷 | 严重度 | 处置 |

| D5 | `launchWeb` 硬编码 **30 s** 启动超时。全新部署后第一次启动 `dsh web` 实测 **>30 s 且完全无输出**，导致"启动 Harness"必然误报失败；重试才成功。本轮 2 次独立复现 + 1 次插桩复现（30 s 内零字节输出） | **P1（功能误报）** | 超时提升到 120 s 且错误信息带上子进程尾部输出；全新部署后立刻跑集成测试 **42.8 s 通过、health=usable** |

| D8 | 卸载残留空程序目录（见 §4） | P2 | 已修复 |

D6 是本次审计最重要的发现：它不需要恶意操作，只要用户在 `install-qqbot` / `verify-plugin` 阶段点"取消 + 清理"，用户已有的 Harness profile 就会被递归删除 —— 直接违反"绝不误删用户 Harness / Profile / API 配置"。
