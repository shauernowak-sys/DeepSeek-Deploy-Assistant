| 项 | 内容 |
|---|---|
| 目标 | 在**不破坏官方 QQ / M3.1** 的前提下，新增独立的个人 QQ 路线（SnowLuma + `dsh-qq-link`），普通用户可只靠图形界面完成 |

## 1. 目标与非目标

### 1.1 目标

1. 用户能选路线（官方 / 个人），个人路线**只依赖图形界面**完成：装组件（或按引导手动装）→ 启动 → 扫码登录 → 打通 Harness → 发消息验证。
2. 两条路线的状态、配置、卸载、数据**完全隔离**。
3. 所有"已联通/可用"结论**必须有运行时证据**（六段式），禁止 `进程在 = 已连接`。
4. 许可证与署名在 UI 与文档里**如实呈现**（含 EULA 原文要点链接）。

### 1.2 非目标

- 不实现 QQ 协议、不做 hook 注入（那是 SnowLuma 的事）。
- 不修改 SnowLuma 的文件（含 `index.mjs`、`native/*`、`node.exe`）。
- 不把 SnowLuma 放进我们的安装包/resources/`release/`。
- 不代用户接受 EULA/PRIVACY。
- 不做第三方组件自动更新（`SNOWLUMA_UPDATE_CHECK=0` 钉版本）。
- 不把个人 QQ 塞进 13 步主部署链（避免拖慢/污染核心部署）。

## 2. 交付形态与放行门

```
             ┌─ S-1 = A（书面授权）→ 形态 A：自动下载/安装/配置/启动
产品决策 ────┤
             └─ S-1 = B/C（未授权）→ 形态 B：官方入口 + 引导 + 检测 + 参数复制
                                    （含"用户已在本地安装时，可由本人点击启动"）

两种形态共用：S2 检测器 / S4 授权引导 / S5 适配层 / S6 验收
```

| 门 | 判据 |
|---|---|
| **G-S1** | 产品方书面确认 S-1/S-2/S-3；若为 A，授权文件已入库 `docs/evidence/snowluma-authorization/` |
| **G-S2** | 检测器单测全绿，且**能在没有 SnowLuma 的机器上**正确返回 `snowluma-not-installed`（不误报） |
| **G-S3** | 形态 A：下载→校验→解压→记录 全链路可重跑、可回滚、可断点；形态 B：引导页每一步都有"下一步去哪" |
| **G-S4** | 用户能在 UI 里拿到 WebUI 地址与一次性密码，并完成扫码登录；失败有可执行原因 |
| **G-S5** | `dsh-qq-bridge/state` 返回 `ok:true` 且 `NapCat状态` 无错；**不得**只凭端口通就判联通 |
| **G-S6** | QQ-GATE-02 的 12 项逐项记录（含"不支持"的如实标注） |

## 4. 个人 QQ 状态机（八相位）

| 相位 | 判定依据 | 用户看到的下一步 |
|---|---|---|
| `qq-missing` | 找不到 `QQ.exe` | 官网下载并安装 QQ |
| `qq-not-running` | 无 `QQ.exe` 进程 | 打开 QQ 并登录 |
| `snowluma-not-installed` | 安装目录/`release.json` 缺失 | 形态 A：点"安装"；形态 B：去官方 Releases |
| `snowluma-installed` | `release.json` 版本可读且与 manifest 一致 | 启动 SnowLuma |
| `snowluma-running` | 进程指向我们的安装目录 **且** 5099 可连 | 打开 WebUI 完成登录 |
| `snowluma-logged-in` | OneBot `get_login_info` 返回真实 QQ 号 | 点"打通 Harness" |
| `harness-linked` | `/dsh-qq-bridge/state` `ok:true` 且 `NapCat状态` 无 `错` | 发一条消息验证 |
| `message-verified` | 有真实往返证据（人工确认 + 证据文件） | —— |

失败态统一附加 `failed`（含原因）与 `evidence[]`（时间 + 来源 + 原文）。

## 5. 数据与安全边界（硬要求）

| 要求 | 实现 |
|---|---|
| 不碰 SnowLuma 文件 | 形态 A 只解压；运行时不改任何文件；形态 B 完全只读 |
| 不代接受协议 | `SNOWLUMA_ACCEPT_EULA/PRIVACY` 只在用户勾选并记录（版本+时间+哈希）后注入 |
| OneBot 令牌 | 只读、内存传递、**不进日志/诊断包/渲染层明文**（UI 只显示掩码与"复制"按钮由主进程写入剪贴板） |
| WebUI 一次性密码 | 只在内存与剪贴板；不落盘；退出即清 |
| 卸载语义 | 只删我们创建的那份组件目录 + `install.json`；`config/`、`data/` 属用户数据默认保留 |
| 不影响官方路线 | 个人路线的任何操作**不触碰** `secrets.bin` 的 `qq.*`、不触碰 `dda:managed:qq` 块 |
| 诊断包 | 沿用 `redact()`；新增字段（OneBot 地址/令牌/密码）必须显式脱敏并加断言测试 |

| 类别 | 用例 |

## 7. 工作量与顺序

| 阶段 | 内容 | 预估 |
|---|---|---|
| S1 | 决策与授权材料（S-1/S-2/S-3）+ 第三方声明 | 0.5 人日 |
| S2 | 契约 + 检测器 + 单测 | 1.5–2 人日 |
| S3 | 形态 B 引导页（4 步） | 1.5 人日 |
| S3-A | 形态 A 下载/解压/记录/卸载 | +1.5 人日 |
| S4 | 启动与授权引导（含日志捕获） | 1–1.5 人日 |
| S5 | 适配层 + bridge 取证 | 1–1.5 人日 |
| S6 | 双路线 UI + 集成测试 + 文档 + 真实验收 | 1.5–2 人日 |

**建议顺序**：`S1 → S2 → S3(B) → S5（先把"能联通"证明出来）→ S6 → 再决定是否投 S3-A/S4 的自动化`。理由：先用最小成本验证真实链路，再决定要不要为自动化付许可与工程的双重成本。

### 11.4 过程中发现并修复的问题

**`errors` 文本可能泄漏 OneBot 令牌**：单测发现 `composePersonalQqStatus` 把传入的 `errors[]` 原样写进证据，而异常消息里可能带 `access_token=`。已在合成层加统一脱敏（默认抹 `access_token=`，调用方可传 `redact` 传入本次已知令牌），并加断言。
